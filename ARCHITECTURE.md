# Архитектура Site Restorer (Rust)

Документ описывает устройство основной реализации. Исходная версия на Python
описана в [legacy/python/ARCHITECTURE.md](legacy/python/ARCHITECTURE.md) —
алгоритмы там те же, отличается язык и GUI-тулкит.

Требования к системе — [TZ.md](TZ.md), единственный документ требований.

## Конвейер

```
[1] Инвентаризация CDX → [2] Параллельная загрузка → [3] Сборка → [4] Проверка → [5] Отчёт
```

Код: `src/core.rs` (движок), `src/app.rs` (окно), `src/main.rs` (точка входа и CLI),
`src/sanitize.rs` (разбор адреса), `src/paths.rs` (адрес → путь), `src/i18n.rs` (строки RU/EN).

### 1. Инвентаризация

1. Пробный запрос `showNumPages=true&output=json` — сколько страниц в CDX.
2. Одна страница → один запрос с `collapse=urlkey&limit=50000`.
3. Много страниц → постраничный обход `&page=i` (до 200), с прогрессом.
4. URL нормализуются (`https`, без `www`, без порта 80/443, без якоря);
   из нескольких снимков берётся самый свежий.

Ответ CDX разбирается своим парсером (`parse_rows`): внешний массив — контейнер,
строка данных начинается с кавычки, шапка `timestamp` отбрасывается.

### 2. Загрузка

- Задачи перемешиваются по типам (html, code, img, other), поэтому все четыре
  полосы прогресса идут одновременно.
- Перед стартом сканируется `mirror/`: файл считается готовым, если существует
  и непустой — повторный запуск продолжает с места остановки.
- Режим `id_`: `http://web.archive.org/web/<ts>id_/<url>` отдаёт исходные байты.
  При 404 перебираются соседние годы.
- Конкурентность: `Gate` на `Mutex + Condvar`, лимит меняется на ходу.
  AIMD-контроллер раз в 3 с: были 429 — лимит вдвое, три окна подряд — пауза
  120 с и сброс к 2; скорость растёт — +1 поток (потолок 24).
- Запись через `.part` + переименование: прерванный файл не считается готовым.

### 3. Сборка оффлайн-копии

Копия `mirror → site` с переписыванием ссылок в относительные:

- атрибуты `href/src/data-src/data-bg/poster/action/data-original` — в кавычках,
  в одинарных кавычках и **без кавычек**;
- `srcset` / `data-srcset` (каждый кандидат отдельно);
- `url(...)` в CSS и inline-стилях;
- `<base>` удаляется, чтобы относительные пути считались от файла.

Кодировки: UTF-8 → объявленная (`meta charset` / `@charset`) → windows-1251;
на выходе всегда UTF-8, объявления приводятся к `utf-8`.

Эвристики (работают для любой CMS):

- кэш с хэшем в имени (Bitrix `bitrix/cache/.../template_<hash>_v1.css`,
  WordPress `?ver=`) → подставляется файл того же типа;
- миниатюры `upload/resize_cache/iblock/<aa>/<size>/<name>` → оригинал `upload/iblock/<aa>/<name>`;
- поиск по имени файла при совпадении глубины пути.

### 4. Проверка

Обход всех HTML в `site/`: считаются внутренние ссылки и битые (учитываются и
одинарные, и двойные кавычки; внешние, `mailto:`, `data:` пропускаются).

### 5. Отчёт

`report.html`: покрытие, объём, разбивка по типам (HTML, CSS/JS, изображения,
прочее), число битых ссылок и ошибок загрузки.

## Интерфейс

- Одно окно на egui: форма, крупная полоса общего прогресса, четыре полосы по
  типам, тёмный журнал, окно справки.
- Движок работает в отдельном потоке и присылает снимки прогресса через
  `mpsc`-канал; окно опрашивает канал каждый кадр.
- Кнопка «Остановить» выставляет `AtomicBool`, который проверяют воркеры и
  этапы сборки.
- Язык RU/EN переключается на лету, строки собраны в `src/i18n.rs`
  (диагностические сообщения движка остаются русскими).

## Сборка

- Один бинарник: `cargo build --release` (GUI + CLI) или
  `--no-default-features` (только CLI, без eframe/rfd).
- Профиль релиза: `opt-level = "z"`, LTO, `panic = "abort"`, strip — отсюда
  2–3,4 МБ для CLI и 6,5–9,1 МБ для GUI.
- Linux CLI собирается на musl: `x86_64-unknown-linux-musl` даёт полностью
  статический ELF (`ldd` → not a dynamic executable).
- GUI на Linux требует системных X11/GL (это норма для нативного окна).

## Платформенные правила и ускорения

Возможности процессора сосредоточены в `src/isa.rs`: определение один раз
(`OnceLock`), строка в отчёте и `--version --verbose`, выключатель
`SR_NO_SIMD=1`. Решение «идти ускоренным путём» принимается не чтением флага, а
получением пропуска `isa::Avx2`; функция с `#[target_feature]` обязана его
принимать. Правило проверяется `scripts/check-flags.py`: `#[target_feature]`,
`is_x86_feature_detected`, `std::arch` и `cfg!(target_feature)` допустимы только
в `src/isa.rs`, флаги сборки — только в `.cargo/config.toml`.

## Известные ограничения

- Нет докачки больших файлов по HTTP Range — файл берётся целиком.
- Нет встроенного локального сервера — копию открывают отдельным сервером.
- При громадных архивах (>200 страниц CDX) инвентарь усекается с предупреждением.
- 32-битные сборки (Windows x86 и Linux i586) не выпускаются с 3.6.1: `ring`
  не собирается под `i686-unknown-linux-musl` без multilib, а Windows-вариант
  удваивал матрицу и нормы размера. Последняя 32-битная версия — 3.6.0;
  решение и последствия — `docs/PLATFORMS.md` §6.

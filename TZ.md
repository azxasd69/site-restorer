## 0. О документе

### 0.1 Назначение

У продукта две реализации, и у каждой уже есть собственное ТЗ, восстановленное
по коду. Этот документ — **свод**: он описывает продукт целиком, в одной
нумерации, и для каждого требования указывает, в какой ветке оно выполнено.
Свод нужен потому, что:

- **требования нельзя читать по одной ветке.** Половина того, что есть в Python
  (сохранение настроек, живые счётчики индекса, машиночитаемый итог CLI), в Rust
  отсутствует; половина того, что есть в Rust (надёжное определение кодировок,
  релизные гейты, живые матрицы), не существует в Python. По отдельности каждое
  ТЗ описывает **реализацию**, а не **продукт**.
- **расхождения должны быть видны как расхождения**, а не как «в этой ветке
  просто не написано»: иначе следующая правка выберет ветку случайно и потеряет
  поведение.
- **приёмка продукта** требует единого набора критериев: что считается дефектом
  независимо от языка реализации.

### 0.2 Метод

Свод построен тремя шагами.

1. **Код → требование** отдельно по каждой ветке (это уже сделано и зафиксировано
   в веточных ТЗ): прочитан весь код — 5654 строки Rust в 11 модулях и 2332 строки
   Python в 3 модулях плюс тесты.
2. **Сверка фактическим прогоном** проверок в обеих ветках:

   | Проверка | Python 2.4.2 | Rust 3.1.3 |
   |---|---|---|
   | Модульные тесты | 17 из 17 (`unittest`, 0,2 с) | 50 из 50 (`cargo test`, 0,11 с) |
   | Форматирование и линтер | нет в проекте | `fmt` и `clippy -D warnings` — код 0 |
   | Гейты зависимостей | нет | `audit`, `deny`, `machete`, `typos` — зелёные в CI |
   | Живые прогоны | не формализованы | 24 CLI-кейса, 9 GUI-кейсов, 3 стенда |
   | Релиз | вручную (`publish.ps1`, тег `v2.4`) | CI по тегу, 8 файлов, лимиты, суммы |

3. **Сведение**: требования объединены по стадиям конвейера и по видам
   обеспечения; совпадающие по смыслу слиты в одну строку, различающиеся
   помечены, отсутствующие в одной из веток помечены явно.

### 0.3 Границы

- Документ описывает требования к **продукту**; веточные ТЗ остаются детализацией
  по реализации (имена функций, тесты, параметры).
- Ни одно требование не выдумано: всё либо реализовано хотя бы в одной ветке,
  либо помечено как пробел (Приложение Б) или сознательное ограничение (§ 4.9).
- Количественные показатели — измеренные значения на конкретных стендах и
  датах; гарантий SLA они не образуют.

### 0.4 Соглашения

- Идентификаторы: `Ц-` цели, `С-` сценарии, `ФТ-` функции, `НД-` надёжность,
  `ПР-` производительность, `БЗ-` безопасность, `ЭР-` эргономика, `СВ-` совместимость,
  `ЭК-` эксплуатация, `ОГ-` ограничения, `РЛ-` поставка и автоматизация,
  `ДК-` документация, `ПРМ-` приёмка, `Р-` решения (Приложение Е), `Б-` пробелы
  (Приложение Б).
- Колонка **«Ветка»** в таблицах требований:

  | Значение | Смысл |
  |---|---|
  | `обе` | требование выполнено в обеих реализациях, критерий одинаков |
  | `обе (по-разному)` | выполнено в обеих, но механика или параметры расходятся; расхождение описано в ячейке «Реализация» и в Приложении Г |

- «Обязательно» — выполнено и покрыто проверкой (тест, гейт, живой кейс);
  «Следует» — выполнено, допускает вариацию в пределах критерия;
  «Не поддерживается» — сознательно вне границ, с причиной.

## 1. Общие сведения

### 1.1 Наименование, обозначение, версии

- Полное наименование: «Site Restorer» — восстановление сайта из веб-архива.
- Изделие: SR. Реализации: **SR-RS 3.1.3** (Rust, edition 2024) — основная,
  развивается и публикуется; **SR-PY 2.4.2** (Python 3.14, tkinter) — архив,
  не разрабатывается, не собирается, не публикуется.
- Комплект поставки: Rust — 7 ассетов и `SHA256SUMS.txt` в релизе; Python —
  исходники и скрипт сборки (археология).

### 1.2 Заказчик, разработчик, пользователи

| Роль | Описание |
|---|---|
| Заказчик | Владелец продукта; принимает результат прогоном и релизом |
| Разработчик | Автор проекта (единственный) |
| Пользователь | Владелец сайта, веб-мастер, подрядчик; один человек за сеанс; без сервера и без прав администратора |

### 1.3 Основание для разработки

Утрата доступа к сайту при наличии снимков в Internet Archive: домен
резолвится, хостинг не отвечает, резервных копий нет. Штатные средства архива
отдают страницы с панелью и переписанными ссылками — для локального просмотра
«как было» они непригодны. Проверено на реальном кейсе `prokupol.ru`
(Bitrix + Aspro Max): 1638 адресов в CDX, 9476 снимков 2016–2026, восстановлено
1609 из 1638 (98,2 %), копия 315 МБ; картинки товаров в архив не попадали
(2510 адресов не сохранены ни разу) — это ограничение источника, а не дефект.

### 1.4 Сроки

Фактические: Python 1.0 → 2.4.2 — 09.11.2026; порт на Rust 3.0.x → 3.1.3 —
10.11.2026 (записи 3.0.0–3.0.6 в `CHANGELOG.md` отсутствуют, см. Б-22).
Плановые сроки не нормируются.

### 1.5 Порядок предъявления результатов

Результат предъявляется как: собранный бинарник, прогон на реальном адресе с
`report.html`, комплект документов, для Rust — зелёный CI на теге, релиз из
8 файлов с контрольными суммами и живые матрицы `tests/live` на трёх стендах.

## 2. Назначение и цели создания

### 2.1 Назначение

По адресу сайта построить локальную статическую копию, пригодную для просмотра
без исходного хостинга, и отчёт о полноте этой копии — без установки зависимостей,
без прав администратора, одним запуском.

### 2.2 Цели и проверяемые признаки

| ID | Цель | Проверяемый признак | Чем подтверждается | Ветка |
|---|---|---|---|---|
| Ц-1 | Копия открывается локально и выглядит как оригинал | Страницы, стили и картинки отдаются из папки `site` любым локальным сервером | Кейс `prokupol.ru`: 1609/1638 адресов, 1164/1168 HTML, 315 МБ; Rust: нагрузочный прогон 1193 страницы | обе |
| Ц-2 | Работает на любом сайте, сохранившемся в архиве | Успешные прогоны на разных CMS без настройки под движок | Python: 5 CMS (Bitrix, WordPress, MODX, Craft, Laravel); Rust: эвристики `Index::resolve` | обе |
| Ц-3 | Пользователь видит, что происходит | Этап, процент, скорость, потоки, ETA, полосы по типам, журнал | Python: 4 полосы и статусная строка; Rust: степпер, 4 плитки, сетка 2×2 | обе |
| Ц-4 | Архив не блокирует за высокую нагрузку | Серия 429 приводит к срезу потоков, паузе и продолжению с того же места | AIMD-контроллер и предохранитель в обеих ветках | обе |
| Ц-5 | Прерванный прогон продолжается, а не начинается заново | Повторный запуск не скачивает готовое | `mirror/` переиспользуется; кейс `load-kill-resume` | обе |
| Ц-6 | Понятно, чего в копии нет | Отчёт: покрытие, объём, типы, битые ссылки, отказы 404, ошибки | `report.html` в обеих ветках | обе |
| Ц-7 | Ноль зависимостей у пользователя | Один исполняемый файл; Python не нужен; CRT статический | PyInstaller-сборка (Python); `+crt-static` и musl (Rust) | обе |
| Ц-8 | Релиз воспроизводим и проверяем | Тег = версия, `--version` у каждого ассета, лимиты размера, суммы, живые ссылки | `build.yml`, `links.yml`, релиз v3.1.3 | Rust |
| Ц-9 | Ввод не требует объяснений | Любая вставка (URL, ссылка из архива или поиска, раскладка, IDN, markdown) приводит к домену | 12 тестов разбора и 9 тестов вставки (Rust), 15 подслучаев (Python) | обе |

### 2.3 Что не входит в цели

| Не делается | Причина |
|---|---|
| Обход капчи, подмена User-Agent под браузер, ротация IP | Провоцирует блокировку «suspected abusive bot traffic»; сознательный отказ |
| Восстановление динамики: корзина, вход, поиск, AJAX | Серверной части в архиве нет |
| Хостинг, публикация и деплой копии | Пользователь поднимает локальный сервер сам |
| Встроенный веб-сервер | Отдельная задача; в обеих ветках отсутствует |
| Работа с платными API и внешними сервисами | Продукт не должен зависеть от чужого биллинга |
| Докачка больших файлов по HTTP Range | Архив отдаёт целые ответы; ценность ниже стоимости |
| Сборки под macOS и 32-битный Linux | Нет стенда и/или TLS-тулчейна |
| Установщик Windows (MSI/Inno) | Отдельный релиз; сейчас портативный exe |

## 3. Характеристика объекта автоматизации

### 3.1 Источник данных: CDX API Internet Archive

Две точки взаимодействия: `web.archive.org/cdx/search/cdx` (индекс) и
`web.archive.org/web/<ts>id_/<url>` (байты снимка).

| Параметр | Python 2.4.2 | Rust 3.1.3 |
|---|---|---|
| Схема обращения | `http` по умолчанию; при редиректе схема берётся из Location, после трёх ошибок соединения принудительно `http` | `http` фиксированно |
| Отбор записей | `matchType=domain`, `filter=statuscode:200`, `collapse=urlkey` | то же |
| Поля ответа | `timestamp, original, mimetype, statuscode` | то же |
| Оценка объёма | `showNumPages=true&output=json`, 3 формата ответа | то же, 2 формата (объект не разбирается, Б-1) |
| Быстрый запрос | `limit=50000`, только если страница одна | `limit=50000`, **всегда**, 3 попытки |
| Постраничный обход | `20000` × `min(pages, 200)`, при отказе — резерв `5000` × 200 | только как резерв `20000` × ≤200 |
| Пауза при отказе | `Retry-After` или `10 + 15 × попытка` с, 3 попытки | `Retry-After` или `10 × попытка` с, 3 попытки |
| Признаки усечения | `≥ 50 000` адресов, `> 200` страниц | `≥ 50 000` адресов, отказ страницы |
| Разбор ответа | `json.loads` | свой парсер `parse_rows` (внешний массив — контейнер, шапка отбрасывается) |

Почему в Rust быстрый запрос выполняется всегда: постраничный режим `page=N`
поддерживается не для всех сайтов, и у части домов он всегда пуст. Дефект
«при `numpages > 1` быстрый запрос не выполнялся, инвентарь получал 1 адрес
вместо тысяч» найден живым тестом и исправлен (`tests/live/README.md`, дефект №9).

### 3.2 Классы восстанавливаемых сайтов

| Класс | Что важно для алгоритма |
|---|---|
| Статические сайты | Ссылки в трёх формах кавычек, `srcset`, CSS `url()`, `<base>` |
| Bitrix (в т. ч. Aspro) | Кэш с хэшем в имени `bitrix/cache/(css\|js)/s1/...`, миниатюры `upload/resize_cache/iblock/...` |
| WordPress, MODX | Параметры версии в ссылках, минифицированные файлы |
| Крупные каталоги и блоги | Тысячи адресов, много типов файлов, обрывы на объёме |
| Старые сайты в cp1251/KOI8-R | Кодировка объявлена неверно или не объявлена вовсе |

Эвристики применяются только как разрешение «файла нет по точному пути» и не
меняют поведение при точном совпадении.

### 3.3 Пользователь и условия работы

Один пользователь. Python: Windows 10/11 x64 или x86. Rust: Windows 10/11
x64/x86 либо Linux x64. Права обычного пользователя, копия на локальном диске,
доступ к `web.archive.org`. В ВМ и RDP без аппаратного OpenGL окно Rust-версии
не откроется — предусмотрены сообщение и CLI.

### 3.4 Сценарии использования

| ID | Сценарий |
|---|---|
| С-1 | Пользователь вставляет адрес (или ссылку из архива/поиска), запускает, видит прогресс, получает `site` и `report.html` |
| С-2 | Прогон прерван (закрытие окна, обрыв сети, лимит архива) — повторный запуск продолжает с места остановки |
| С-3 | Архив ответил серией 429 — инструмент снижает потоки, ждёт, продолжает без вмешательства |
| С-4 | Нужен автоматический прогон — запуск через CLI с параметрами и разбором результата |
| С-5 | Работа в ВМ или удалённом сеансе без OpenGL — окно объясняет причину и предлагает CLI-сборку |
| С-6 | Второй прогон на ту же папку, чтобы докачать то, чего не хватило (лимит, обрыв, недоступный файл) |

### 3.5 Стенды приёмки

| Код | Система | Что проверяется |
|---|---|---|
| H | Windows 11 Pro x64 (хост) | GUI x64, CLI x64, WOW64 для x86, нагрузка |
| V | Windows 10 Pro x86 (Hyper-V, 2 vCPU / 3 ГБ), чистая, без VC++ Redist | настоящая 32-битная система, статический CRT, GUI без OpenGL |
| L | Ubuntu 24.04 LTS (Hyper-V, 4 vCPU / 4 ГБ, Xvfb) | musl-CLI, glibc-GUI, системные библиотеки |

Python-ветка проверялась на H (Windows 11) и на копиях файловых баз; формальной
матрицы у неё нет.

#### 4.1.2 Конвейер

Пять последовательных стадий в обеих ветках:
инвентаризация → загрузка → сборка → проверка → отчёт.

| Свойство | Python | Rust |
|---|---|---|

### 8.2 Что считается дефектом

Независимо от ветки:

- Текст в копии не читается или «кракозябры».
- Ссылка в копии ведёт на абсолютный адрес исходного домена.
- Файл, присутствующий в архиве, отсутствует в `mirror/` без записи в «ошибки».
- Падение вместо сообщения при отказе архива.
- Расхождение чисел `report.html` с содержимым `site/`.
- Файл, который можно принять за готовый, но который неполон (нарушение атомарности).
- Имя ассета в релизе не совпадает с обещанным в README и на лендинге.
- Бинарник не запускается на чистой системе целевой платформы.

## Приложение Е. Реестр решений

| ID | Решение | Почему | Следствие |
|---|---|---|---|
| Р-1 | Python-версия — только стандартная библиотека | ноль зависимостей и простая упаковка | нет готовых парсеров HTML/CSS; свой разбор регулярками |
| Р-2 | Rust + egui — единственная развиваемая реализация | один самодостаточный бинарник, нативное окно | Python и Go заархивированы, их сборки не публикуются |
| Р-3 | Свой punycode вместо `idna` | `idna` тянет ICU4X и десятки крейтов ради одной функции | нет нормализации UTS-46; проверка формы метки вручную |
| Р-4 | Свой детектор кодировок вместо `chardetng` | минус зависимость, плюс контроль над решением | эвристики (хи-квадрат частот) требуют тестов — их 13 |
| Р-5 | Свой слой буфера обмена на Windows | встроенный путь не читал буфер другого процесса | WinAPI-код в `clip.rs`, стабы для других ОС |
| Р-6 | Свой диалог папки на `SHBrowseForFolderW` | `rfd` — лишняя зависимость | на не-Windows диалога нет (Б-2) |
| Р-7 | `regex-lite` вместо `regex` | размер бинарника | нет части синтаксиса; шаблоны написаны под ограничения |
| Р-8 | Статический CRT на Windows | exe без Visual C++ Redistributable (проверено: без него код `0xC0000135`) | размер чуть больше, зато запуск на чистой системе |
| Р-9 | musl для Linux CLI | полностью статический ELF, работает в любом дистрибутиве | GUI всё равно требует системных X11/GL |
| Р-10 | Быстрый запрос CDX всегда, постранично только как резерв | постраничный режим у archive.org поддерживается не для всех сайтов | один запрос на инвентарь в большинстве случаев |
| Р-11 | AIMD 2 → 24 с предохранителем на серию 429 | потолок задаёт архив, а не канал | при 429 скорость падает, но прогон продолжается |
| Р-12 | Имена ассетов без версии, 8 файлов в релизе | ссылки `releases/latest/download/<имя>` постоянны | версия только в `--version`, теге и CHANGELOG |
| Р-13 | Текст релиза ставит `gh release edit --notes-file` | `softprops` при пустом `body` молча оставлял старый текст | отдельный шаг с `GH_TOKEN` |
| Р-14 | Тулчейн закреплён (`rust-toolchain.toml`) | релиз не зависит от того, какой stable попал на раннер | обновление версии — вместе с CHANGELOG |
| Р-15 | Отказ от обхода лимитов архива (капча, подмена UA, ротация IP) | маскировка под браузер провоцирует блокировку | медленнее, но устойчиво и этично |
| Р-16 | В Rust не хранится состояние между запусками | меньше поверхности (нет файла, нет миграций) | признано регрессом против Python (Б-3) |
| Р-17 | Python и Go оставлены в репозитории как история | видно происхождение алгоритмов | два мёртвых каталога, исключены из CI |

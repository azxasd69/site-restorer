Background

Born out of an outage, not out of an idea

On the night of 1–2 November 2026, the hosting provider Beget suffered an attack on its infrastructure management plane. The provider confirmed the loss of customer data: virtual server contents, S3 object storage and Kubernetes clusters, with VPS binary backups lost as well.

The site this project started with was hosted there: the domain still resolved, the server did not respond, and no backups existed. The only remaining source was the web archive — 1,638 URLs and 9,476 snapshots spanning ten years.

Coverage: 3DNews, Habr, DW.

If your site was affected by the same outage, start with the archive — not with panic.
Text and structure usually survive in full: pages, articles, the whole catalogue. What tends to be missing is product imagery and anything dynamic.

Features

Everything between a domain name and a working copy

The app does four things: finds out what the archive kept, downloads it, assembles an offline copy and verifies the result.

Archive inventory

The CDX index of the Internet Archive: every captured URL of the domain. Paged crawl for large sites, up to 50,000 URLs per run.

Parallel downloading

HTML, CSS, scripts and images are fetched concurrently. Concurrency adapts by AIMD: 2 → 24 workers, backing off on HTTP 429.

Resume and resilience

Nothing already downloaded is requested twice. An interrupted run continues where it stopped, and archive rate limits are handled with backoff rather than errors.

Offline build

Absolute links are rewritten to relative ones. CMS caches with hashes in filenames and image thumbnails are handled heuristically, so styles and pictures do not break.

Verification and report

Every built page is scanned; internal and broken links are counted. report.html shows coverage by file type, total size and the list of errors.

Any address, any CMS

A link from an email, a search result or the archive itself; wrong keyboard layout; IDN domains. Tested on Bitrix, WordPress, MODX, Craft CMS and Laravel.

How it works

Four steps, no configuration

  1. Paste an address

    A domain, a link with tracking parameters or an archive URL. The input is cleaned automatically, including wrong keyboard layout and IDN.

  2. Pick a folder

    Defaults to Documents\SiteRestore\site. Any drive and directory will do.

  3. Press “Start”

    Downloading runs in the background: progress by file type, a request log, and a “Stop” button at any moment.

  4. Open the report

    report.html shows coverage, size and broken links. Serve the copy with a local web server.

PowerShell 
cd Documents\SiteRestore\site
python -m http.server 8080

Why a server. The copy is plain HTML, but links like /catalog/ will not resolve when the file is opened by double-click. Any local static server works; if Python is installed, the two lines on the left are enough.

What did not come back, and why

  • Product images. 2,510 images were never captured: the CDX index has no records and replay returns 404 for every year. That is an archive loss, not an app failure.
  • CMS dynamics. Cart, sign-in, search and AJAX catalogue filters do not work in a static copy — they need a backend and a database.
  • Template cache. Asset filenames carry a build hash. The app substitutes a file of the same type: styles survive, the exact version may differ.

Limits

What to know before you start

No promises of magic: the tool carefully extracts what the archive actually preserved.

Only what was saved

If the Internet Archive crawler never fetched a file, it is missing from every snapshot. The report says so instead of substituting a placeholder.

Static, not a CMS

The copy is pages and assets. Forms, sign-in, cart, search and AJAX will not work: content and structure are what comes back.

Archive speed

The Internet Archive throttles requests from a single IP. Large sites take hours, which is normal — resuming makes it survivable.

Ethics and law. The tool is meant for archiving and restoring your own sites. It does not bypass protection, spoof the User-Agent or disguise itself as a browser. A copy of someone else's site is not a licence to publish it; respect the Internet Archive terms and the rights of content owners.

FAQ

The short answers

Do I need Python or anything else?
No. The main build is a single Rust binary with no interpreter, so it runs on a clean Windows install. Python is only useful if you want to serve the copy with python -m http.server — any other static server will do as well.
What if the archive saved nothing?
The report will say so, and the app will not invent content. It is still worth trying domain variants (with and without www) and nearby years: for every URL the closest snapshots are probed.
How long does a restore take?
It depends on the site and on archive limits. A small site takes minutes; thousands of URLs take hours, because the Internet Archive throttles requests from one IP. Progress, size and elapsed time are shown in the window, and resuming lets you stop and continue later.
Will product images and photos come back?
Only if the archive captured them. Internet Archive crawlers often save pages but not every image: in one case 2,510 product images were missing from the archive entirely, while the text content survived.
Will the cart, sign-in and search work?
No. The copy is static: pages, styles, scripts and files are restored. Anything that needs server-side logic and a database — cart, authentication, AJAX filters — will not work.
Is this legal?
The tool is built for restoring your own sites. It does not bypass protection, spoof the User-Agent or hide itself. Publishing a copy of someone else's site is not allowed; the Internet Archive terms and content owners' rights must be respected. The app itself is MIT licensed.

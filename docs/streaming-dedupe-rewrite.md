Документ разбирает четыре доработки, отобранные из сравнения с другими инструментами
восстановления сайтов (monolith, wabac.js, wget `-k`, HTTrack, browsertrix) и из списка
кандидатов в [build-performance.md](build-performance.md):

| 1 | Потоковая запись файлов при загрузке | Д-50 |

| 3 | Правка скриптов только при наличии цели в копии | Д-52 |
| 4 | Один проход по документу для атрибутов и наборов источников | Д-53 |

Требования — ТЗ §4.2.11 (ФТ-142…ФТ-148) и §4.4 (ПР-11, ПР-12), пункты плана — 3.8.0.
Смежные документы: [snapshots.md](snapshots.md) (выбор снимка), [build-performance.md](build-performance.md)

## 1. Исходное состояние (3.5.2)

Код: `src/core.rs`.

| Место | Что делает сейчас |

Замеры стенда `rufence.ru` (5394 файла, 756 МБ, 3932 страницы, 1,44 млн ссылок, 22 ядра) из

## 2. Пункт 1. Потоковая запись

### 2.1 Задача

Сейчас тело файла целиком лежит в памяти, пока не будет записано. При 24 потоках пик памяти равен
сумме размеров одновременно читаемых файлов: видеоролик на 200 МБ даёт до 4,8 ГБ. Проверка
ПР-7 («память не растёт заметно для пользователя») выполняется на наборе, где крупных файлов нет,
поэтому дефект не виден до первой копии с медиа.

### 2.2 Варианты

| Вариант | Суть | Итог |
|---|---|---|
| A. Оставить как есть | полный буфер в памяти | Риск падения на копии с крупными медиа; ничего не ломает |
| B. Поток для всех файлов | читать блоками и сразу писать; страницы разбирать потом с диска | Двойное чтение страниц (сначала запись, потом разбор) — против ФТ-124 и радиуса «без лишних проходов»; сложнее |
| C. Гибрид: текст в памяти до предела, остальное потоком | предел 4 МБ (`--text-limit`); текст больше предела сохраняется потоком и считается двоичным | Память ограничена произведением «потоки × предел»; страницы не читаются дважды; поведение на крупных медиа исправлено |
| D. Поток + докачка по частям (Range) | плюс возобновление файла с середины | Закрывает ОГ-4, но требует `If-Range`/`ETag` от архива и состояния на каждый файл; отдельная задача, не в этом пакете |

**Решение — C.** Довод: разбор страницы всё равно требует полного текста в памяти (определение
кодировки, `looks_like_markup`, `is_error_page`), а крупные файлы разбирать не нужно — их надо
только сохранить. Гибрид даёт ограничение памяти без второго чтения и без новых зависимостей.

### 2.3 Как устроить

1. `attempt` получает заголовки; для 200 решает по типу: текст (`html`, `htm`, `css`, `js`, `xml`,
   `txt`, `json`, `svg`) — в память с пределом; остальное — потоком.
2. Если `Content-Length` больше предела — сразу поток, без чтения в память (не тратим память зря).
3. Поток: `BufWriter::with_capacity(64 * 1024)` на `.part`, чтение блоками по 64 КБ, счётчики
   `bytes`/`win_bytes` пополняются по ходу (сейчас — раз в файл, из-за чего скорость «дёргается»).
4. Отмена проверяется между блоками: остановка прекращает чтение за время не более одного блока,
   `.part` удаляется (сейчас отмена ждёт конца файла).
5. По завершении — `rename`, проверка фактического размера (ФТ-35 остаётся), запись типа
   содержимого (ФТ-43) по первым байтам (они есть: первые 4 КБ читаются до решения).
6. Текст, превысивший предел, сохраняется потоком и **не переписывается**: в копии он окажется
   с абсолютными адресами. В журнал — строка «текст больше предела: не переписан — <путь>»,
   в отчёт — счётчик. Это осознанный размен: такой файл почти всегда не страница (лог, дамп,
   минифицированный бандл), а память дороже.

### 2.4 Что проверяется

- Файл 1 ГБ из локального стенда скачивается, копия побайтово равна источнику, пик памяти процесса
  не превышает 100 МБ при 24 потоках (ПР-11).
- Остановка во время большого файла: чтение прекращается не позднее одного блока 64 КБ,
  файла `.part` не остаётся, счётчики не растут после остановки (ФТ-142, ФТ-144).
- Копия `enc-rdbzh` собирается побайтово как раньше (переписывание не тронуто).

### 2.5 Риски

| Риск | Смягчение |
|---|---|
| Предел 4 МБ обрежет настоящую страницу | Предел — параметр; в отчёт и журнал попадает каждый случай; на стенде крупнейшая страница 716 КБ (в 5,6 раза меньше предела) |
| Поток и проверка пригодности расходятся | Первые 4 КБ буферизуются и проверяются до записи основного тела |
| Ошибка записи на середине | `.part` удаляется, файл считается ошибкой; поведение как сейчас (ФТ-34, ФТ-35) |

## 3. Пункт 2. Признак содержимого и дедупликация

### 3.1 Проверка предпосылки (замеры 11.11.2026)

Индекс архива отдаёт поле `digest` (SHA-1 в base32, отпечаток полезной нагрузки). Проверено на двух
доменах, по 2000 строк каждый (`matchType=domain`, `filter=statuscode:200`, `collapse=urlkey`):

| Домен | Строк | Без `digest` | Групп с одинаковым `digest` | Лишних загрузок при дедупликации |
|---|---|---|---|---|
| `rufence.ru` | 2000 | 0 | 10 | 11 (0,55 %) |
| `nginx.org` | 2000 | 0 | 7 | 7 (0,35 %) |

Что видно в данных:

- Дубликаты — это **варианты адреса с параметрами**: cache-buster Bitrix
  (`kernel_socialservices.js?14520041161659` и `…?14570898471659`), `?ref=`, `?_ga=`.
  Один и тот же байт-в-байт ответ под несколькими адресами.
- `length` в индексе — длина **записи в архиве** (со сжатием), а не полезной нагрузки: у файлов с
  одинаковым `digest` длина различается (1161 и 1159). Значит ключ дедупликации — только `digest`,
  `length` для сверки не годится.

Отсюда честная оценка: дедупликация экономит **0,3–0,6 % загрузок** на «обычных» доменах и заметно
больше на сайтах с cache-buster в адресах ресурсов. Сама по себе такая экономия не оправдала бы
работу. Ценность пункта в другом — см. 3.4.

### 3.2 Варианты

| Вариант | Что даёт | Цена |
|---|---|---|
| A. Считать хеш локально после скачивания | дедупликация **не** экономит трафик (файл уже скачан); только учёт | нужен свой SHA-256 (новый крейт) либо FNV (слабее) |
| B. Брать `digest` из индекса до скачивания | экономит трафик и время; ключ известен до запроса файла | +1 поле в инвентаре, дедупликация в загрузке, «алиасы» в зеркале |
| C. Только признак неизменности для сборки | не переписывать то, чьи байты не изменились | без дедупликации: 11 лишних загрузок на 2000 адресов остаются |
| D. Свой SHA-256 на всё | «правильный» хеш локально | пятая зависимость (нарушает §5.2 ТЗ) либо свой SHA-256 в 250 строк |

**Решение — B и C вместе.** Индекс уже содержит хеш, и он же служит признаком неизменности для
сборки: скачали тот же снимок — `digest` тот же — переписывать нечего.

### 3.3 Дедупликация в загрузке

1. Инвентаризация запрашивает `fl=timestamp,original,mimetype,statuscode,length,digest`
   (добавление поля в запрос — одна строка).
2. Адреса группируются по `digest` (пустой `digest` — группа из одного адреса).
3. Канонический адрес группы — самый свежий снимок (при равенстве — лексикографически меньший
   путь, чтобы результат был детерминированным).
4. Канонический скачивается; остальные адреса в загрузке пропускаются и получают файл в зеркале
   жёсткой ссылкой (`fs::hard_link`), при отказе файловой системы — копированием.
5. Если канонический адрес не дал файла (404, ошибка, «непригодный снимок»), остальные адреса
   группы скачиваются обычным путём — правило «дедупликация только поверх полученного».
6. В инвентаре у алиаса появляются поля `digest` и `same_as` (путь канонического файла); формат
   расширяется добавлением полей (СД-3), старый инвентарь читается как раньше.
7. Учёт: `ok` считает полученные адреса как и раньше, отдельный счётчик `shared` — сколько файлов
   получено без запроса; в отчёте строка «совпало по содержимому: N (запросов не делалось)».
   Инварианты ПРМ-8 и ФТ-119 сохраняются: число файлов `site/` и `mirror/` по-прежнему совпадает
   с пересчётом папок, а число адресов объясняется новым счётчиком.

Почему жёсткая ссылка, а не копия: файлы в зеркале не изменяются после загрузки (сборка читает
зеркало и пишет в `site/`), поэтому одна физическая копия на несколько путей безопасна и не
удваивает объём. Если ссылку создать нельзя (другой том, ФС без ссылок) — копирование, объём
вырастет, поведение останется верным.

### 3.4 Признак неизменности в сборке

Сейчас пропуск пересборки опирается на `size` + `mtime` зеркала. Два следствия:

- перекачали тот же байт-в-байт снимок (новый `mtime`) — переписывается вся страница, хотя
  содержимое не изменилось;
- наоборот, файл, у которого изменилось только время, считается новым.

С `digest` в журнале условие становится содержательным: пропускать пересборку, если `digest`
и `size` совпали и файл копии существует. Это же снимает главный остаток замера: «запись 725 МБ
при 30 МБ/с ≈ 24 с» — на повторном прогоне без изменений в архиве переписывать нечего.

### 3.5 Что проверяется

- Стенд с двумя адресами одного содержимого (`/a.js?1` и `/a.js?2`): один запрос к архиву,
  в зеркале два файла, `shared = 1`, файлы идентичны побайтово.
- `rufence.ru`, 2000 адресов: число запросов к архиву уменьшается ровно на число групп-дубликатов;
  копия побайтово совпадает с копией без дедупликации (сверка дерева `site/`).
- Отказ канонического адреса: алиасы скачиваются сами, копия полная, в журнале строка о снятии
  дедупликации для группы.
- Повторный прогон без изменений в архиве: переписано 0 файлов, время сборки падает до замера
  «повторная сборка» (10,6 с на стенде) независимо от `mtime`.

### 3.6 Риски

| Риск | Смягчение |
|---|---|
| `digest` в архиве считает не то (запись вместо полезной нагрузки) | правило «дедупликация только по полученному»: канонический файл скачан и проверен по размеру; алиасы сверяются с ним размером |
| Ошибка архива: одинаковый `digest` у разного содержимого | при расхождении размеров алиас скачивается сам (проверка на этапе загрузки) |
| Жёсткие ссылки на Windows | `fs::hard_link` на NTFS работает в пределах тома; при отказе — копирование |
| Отчёт «поехал» | счётчик `shared` и пояснение в отчёте; автотест ПРМ-8 расширяется |

## 4. Пункт 3. Правка скриптов только при наличии цели

### 4.1 Как сейчас и чем это плохо

`site_rx` (шаблон `^(https?:)?//(www\.)?<хост>(:\d+)?(/…)`) применяется к **всему** тексту `.js`:
каждое совпадение заменяется корневым путём. Что ломается:

- `var api = "https://site.ru/api/v1"` → `"/api/v1"` — в копии такого файла нет, запрос уйдёт
  в никуда; исходный адрес хотя бы работал при живом сервере;
- сравнения вида `if (url === "https://site.ru/page")` перестают совпадать с тем, что приходит
  из `location`;
- адреса, которые скрипт строит для другого домена по шаблону, режутся по префиксу.

При этом **встроенные** скрипты в HTML не правятся вовсе (шаблон атрибутов их не трогает), то есть
правило «абсолютные адреса своего домена заменяются» выполняется для внешних файлов и не
выполняется для встроенных — расхождение внутри одной функции.

### 4.2 Варианты

| Вариант | Итог |
|---|---|
| A. Не трогать `.js` вообще | Максимально предсказуемо, но ссылки на локальные копии внутри скриптов перестанут находиться (сейчас иногда находятся) |
| B. Править только те адреса, чья цель есть в копии (как у атрибутов) | Одно правило на страницы и скрипты; ломающих замен нет; остальные адреса остаются абсолютными |
| C. Править по расширению (`\.(js|css|png|jpg…)`) | Близко к B, но ошибается на адресах без расширения и на страницах |
| D. Разбирать JS синтаксически | Требует разборщика (зависимость или свой), вне бюджета и вне §5.2 |

**Решение — B.** Правило становится единым: `rewrite_ref` уже возвращает исходное значение, если
цель не найдена в копии; для `.js` нужно то же решение вместо безусловной замены.

### 4.3 Что добавить

- Счётчики: «переписано в скриптах N», «оставлено абсолютных M»; в журнал — до трёх примеров
  оставленных адресов, в отчёт — строка «в скриптах осталось абсолютных адресов: M».
- Оставленный адрес — не дефект копии и не битая ссылка: он ведёт на исходный сайт, как и было в
  оригинале. В отчёте это сказано явно, чтобы число «битых ссылок» не путали с ним.
- ФТ-61 уточняется (новая формулировка: «править только адреса, чья цель есть в копии»),
  учёт оставленных адресов — отдельное требование ФТ-147; ФТ-62 (якоря, почта, телефон,
  `javascript:`, `data:`) не меняется.

### 4.4 Что проверяется

- Скрипт с тремя адресами: существующий файл (переписан), `/api/v1` (оставлен), строка сравнения
  (оставлена). Числа в журнале и отчёте совпадают.
- Копия `rufence.ru`: число «переписано» не уменьшилось более чем на 5 % (адреса реальных ресурсов
  в копии есть), «оставлено» > 0 и в отчёте объяснено.
- Встроенный скрипт в HTML: поведение прежнее (не правится), в отчёте это не отражается как дефект.

## 5. Пункт 4. Один проход по документу

### 5.1 Зачем, если сборка дисковая

Из [build-performance.md](build-performance.md): после перехода на `regex` 1.13 скорость шаблонов
выросла с 3,3 до 274 МБ/с, но документ по-прежнему проходит четыре прохода (атрибуты, `srcset`,
`url()` в CSS, `<base>`), то есть 694 МБ сканируются 2,5 раза: 497 с процессорного времени на
22 ядрах. Сборка стала дисковой (запись 24 с из 63 с), поэтому на многоядерной машине объединение
проходов даст немного.

На слабой машине картина обратная: при 2 ядрах те же 497 с процессорного времени — это ≈ 250 с
стены против 24 с записи, и объединение проходов сокращает именно их. Пользователь с ноутбуком
и медленным диском получает выигрыш, пользователь с 22 ядрами — почти нет.

### 5.2 Варианты

| Вариант | Проходов | Риск |
|---|---|---|
| A. Оставить четыре | 4 (+2 в приведении кодировок) | ничего не ломаем |
| B. Объединить атрибуты и наборы источников | 3 | средний: меняются захваты групп, нужна побайтовая сверка |
| C. Объединить ещё и `url()` в CSS | 2 | выше: контекст CSS и атрибутов разный, `url()` встречается и в `style` |
| D. Свой разбор HTML по байтам вместо шаблонов | 1 | высокий: это уже SAX, зависимость или сотни строк |

**Решение — B.** Ровно то, что запрошено, минимальный риск, одна альтернация на два шаблона.
C — кандидат на следующий раз, если B покажет себя.

### 5.3 Схема

Один шаблон с двумя ветками альтернации:

```
(?i)(?:
   (href|src|data-src|data-bg|poster|action|data-original)\s*=\s*
       (?:"([^"]*)"|'([^']*)'|([^\s"'<>`=]+))      // ветка 1: атрибут, группы 1…4
 | (srcset|data-srcset)\s*=\s*
       (?:"([^"]*)"|'([^']*)')                      // ветка 2: набор, группы 5…7
)
```

В замыкании замена выбирается по тому, какая ветка сработала: `caps.get(1)` — атрибут (кавычки
сохраняются по номеру группы, как сейчас), иначе — набор источников (деление по запятой,
дескрипторы плотности сохраняются, ФТ-58). Ветка `srcset` не перехватывается первой: после `src`
шаблон требует `\s*=`, а видит `set=` — совпадения нет, срабатывает вторая ветка. Это свойство
надо закрепить тестом: `srcset`, `data-srcset`, `src`, `data-src` в одном документе.

`url()` и `<base>` остаются отдельными проходами.

### 5.4 Что проверяется

- Побайтовая сверка дерева `site/` до и после на контрольных копиях: `centr-58`, `enc-rdbzh`,
  `rufence.ru` (весь набор), `load-final`. Различий быть не должно ни в одном файле.
- Замер `SR_PROF=1` на `rufence.ru`: процессорное время переписывания не выше 250 с (было 497 с),
  полная сборка не медленнее 63 с.
- Тест на совместное присутствие `src`, `data-src`, `srcset`, `data-srcset`, атрибутов без кавычек
  и в одинарных кавычках.

## 6. Порядок работ и оценки

| Пункт | План | Зависит от | Объём | Что даёт |
|---|---|---|---|---|
| Потоковая запись | Д-50 | — | M (полдня) | Память не зависит от размера файла; счётчики по байтам; отмена внутри файла |
| Признак содержимого и дедупликация | Д-51 | Д-47 (метка журнала), формат инвентаря | M (полдня — день) | Меньше запросов на повторном содержимом; повторная сборка без перезаписи |
| Правка скриптов | Д-52 | — | S (2–3 часа) | Скрипты не ломаются; единое правило со страницами |
| Один проход | Д-53 | Д-52 (тот же участок кода) | S (2–3 часа) | Минус два прохода, минус две копии строки |

Порядок внутри релиза: Д-52 и Д-53 вместе (одна правка `build`), затем Д-50, затем Д-51
(Д-51 трогает загрузку и инвентарь, его лучше делать последним, когда поток уже устоялся).

Почему релиз 3.8.0, а не 3.6: 3.6 — интерфейс и платформы (журнал, настройки, диалог папки),
правило 5 плана не смешивает крупную правку ядра с интерфейсной. Кроме того, Д-18 (раздельные
таймауты) из 3.6 правит тот же сетевой слой — делать потоковую запись после него дешевле.

## 7. Что сознательно не делается

| Не делаем | Почему |
|---|---|
| Докачка файла по частям (Range) | Закрытие ОГ-4 требует состояния на каждый файл и `If-Range`; отдельная задача. Потоковая запись — только фундамент |
| Свой SHA-256 и пятая зависимость | §5.2 ТЗ ограничивает прямые зависимости четырьмя; `digest` из индекса даёт нужное свойство без крейта |
| Разбор HTML/JS синтаксически (SAX) | Дорого, тянет зависимость, а контракт продукта — «байты как в архиве, кроме переписанных ссылок» |
| Отдельный дисковый кэш между загрузкой и сборкой | Роль кэша уже играет `mirror/`; третий экземпляр данных не нужен |
| `fsync` | Ставка на кэш ОС и атомарную подмену `.part` → `rename`; риск потери последних файлов при отключении питания принят (ОГ) |

## 8. Риски пакета

1. **Потоковая запись трогает путь сохранения** — самый нагруженный участок. Смягчение: гибрид
   вместо полного потока, проверки ФТ-34/ФТ-35 остаются, побайтовая сверка копий, тест на отмену
   внутри файла.
2. **Дедупликация меняет числа отчёта.** Смягчение: `shared` отдельным счётчиком, ПРМ-8 расширяется
   автотестом, ФТ-119 сохраняется.
3. **Одинаковый `digest` у разного содержимого** (ошибка архива). Смягчение: сверка размеров,
   самостоятельная загрузка алиаса при расхождении.
4. **Объединённый шаблон меняет разбор** — цена ошибки высокая (порча всех страниц). Смягчение:
   побайтовая сверка на четырёх копиях обязательна, без неё пункт не принимается.

## 9. Как проверять

```powershell
# сборка и тесты
cargo fmt --check; cargo clippy --all-targets -- -D warnings; cargo nextest run

# побайтовая сверка копий до/после (эталон снимается до правки)
python scratch\cmp-tree.py --a <эталон>\site --b <после>\site

# замеры сборки без сети
$env:SR_PROF='1'; $env:SR_BENCH_INVENTORY='<папка>\data\inventory.jsonl'; $env:SR_BENCH_NO_RESCUE='1'
site-restorer.exe --cli --site rufence.ru --out <папка>

# дедупликация: инвентарь и число запросов
site-restorer.exe --cli --site nginx.org --out <папка> --limit 400
# в отчёте: «совпало по содержимому: N (запросов не делалось)»
```

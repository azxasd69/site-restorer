# Полнота индекса архива и добор адресов на ходу

Проработка требования владельца от 11.11.2026 (высокий приоритет): во время скачивания должен быть
получен максимально полный индекс архива, выполнена сверка, и всё, что не попало в очередь в начале,
добавлено в неё — в том числе на этапе сборки копии. Все числа ниже получены запуском против
`web.archive.org` 11.11.2026, а не взяты из документации.

---

## 1. Как устроен индекс и где он теряет адреса

CDX API отдаёт список сохранённых адресов. Проверено на четырёх запросах к `nginx.org`, `prokupol.ru`
и `lenta.ru`.

| Приём | Что делает | Замер |
|---|---|---|
| `url=<host>` без `matchType` | трактуется как **точный** адрес: возвращает один адрес со всеми снимками | `url=nginx.org` + `filter=statuscode:200` → 11 400 строк, но `collapse=urlkey` → **1** адрес |
| `matchType=prefix` | всё под префиксом | `nginx.org` → 50 000 строк при `limit=50000` (упёрлось в лимит) |
| `matchType=domain` | домен и поддомены | `nginx.org` → **504 за 60 с**; `prokupol.ru` → 1 637 адресов, но 1 из 2 попыток дала **503** |
| `collapse=urlkey` | схлопывает варианты одного адреса (`http`/`https`, `www`, `:80`) | без него те же данные приходят в 2–3 раза длиннее |
| `filter=statuscode:200` | выбрасывает снимки ошибок | 27 781 → 11 400 строк на корне `nginx.org` |
| `limit` | **обрезает молча** | `nginx.org` + prefix + collapse: `limit=50000` → ровно 50 000, `limit=100000` → **70 291**; потеря 20 291 адреса (29 %) |
| `page=N` + `showNumPages` | постраничный обход | `prokupol.ru`: 3 страницы (518 + 968 + 152) = **1 638**, и столько же отдаёт запрос без `limit` — обход **сходится точно** |
| `pageSize=N` | **не работает как ожидается** | `pageSize=100` и `pageSize=1000` на `prokupol.ru` дают «1 страница» вместо 17 и 2 — параметру доверять нельзя |
| `showResumeKey=true` | постраничный курсор вместо номеров | работает: ответ заканчивается `[]` + ключ (`eJwr…`), обход можно продолжать без пересчёта страниц |
| `to=<метка>` | фиксирует верхнюю границу выборки | нужен, потому что индекс живёт: один и тот же запрос вернул 518 и 517 строк в двух запусках подряд |

Отдельно измерено, сколько страниц бывает у больших доменов:

| Домен | `showNumPages` | Что это значит при текущем пределе 200 страниц |
|---|---|---|
| `prokupol.ru` | 3 | покрытие полное |
| `nginx.org` | 98 | покрытие полное |
| `lenta.ru` | **5 401** | **3,7 %** — остальное отбрасывается молча |

Устойчивость под нагрузкой: серия из 12 тяжёлых запросов прошла без ошибок, но в серии из четырёх
запросов `domain`/`prefix` два ответа были **503**, а `matchType=domain` на `nginx.org` стабильно
уходит в **504**. То есть 503/504 — не редкость, а рабочий режим: их надо переживать повторами и
считать признаком неполноты, а не «пустым архивом». Это же подтверждает практика `prokupol.ru`
(см. `plans/2026-11-prokupol-archiv-metod.md`, проблема П2): архив отдаёт 503/504 молча, пустым ответом.

## 2. Что из этого следует для Site Restorer

Сейчас инвентаризация делает так (`src/core.rs`, `inventory`):

1. `showNumPages=true` — оценка числа страниц (только для сообщения в журнале);
2. **быстрый запрос** `matchType=domain`, `collapse=urlkey`, `filter=statuscode:200`, `limit=50000`;
3. если быстрый ответ пуст — постраничный обход до `MAX_PAGES` (200).

Три дефекта следуют прямо из замеров:

- **Д1. Усечение не отличается от полноты.** Список ровно в 50 000 строк означает «дальше не просили»,
  а не «дальше нет». На `nginx.org` это 29 % адресов; сейчас в журнал пишется строка «список обрезан»,
  но прогон продолжается так, будто список полный.
- **Д2. Предел 200 страниц.** У `lenta.ru` их 5 401: копия собирается по 3,7 % истории, и в отчёте
  это никак не видно.
- **Д3. `matchType=domain` на крупных доменах ловит 504**, а 503 приходит и на малых: без повторов и без
  признака «индекс не получен» прогон может начаться с пустого или частичного списка.
- **Д4. Индекс живёт.** Между двумя одинаковыми запросами число строк меняется (518 → 517): без
  зафиксированной верхней границы «полнота» недоказуема.

Плюс то, чего в текущей схеме нет вообще: **сверка после начала загрузки**. Всё, что появилось в
индексе или было пропущено из-за лимита, в очередь уже не попадает — прогон идёт по снимку списка,
снятому в начале.

## 3. Решение: три окна сверки

```
[1] старт:        полный обход индекса (до конца, с контролем усечения и водяным знаком)
                  ↓ очередь адресов
[2] загрузка:     каждые N файлов / T секунд — запрос «что нового после водяного знака»
                  → новые адреса сразу в очередь, без перезапроса известных
                  ↓ зеркало
[3] сборка копии: ссылка, цели которой нет ни в копии, ни в очереди → адрес в очередь
                  → добор → пересборка затронутых страниц
                  ↓
[4] итог:         финальная сверка «индекс против копии» и раздел «Полнота индекса» в отчёте
```

Ключевые решения:

- **Обход до конца, а не до 200 страниц.** Предел остаётся, но он параметр (`--index-max-pages`), и его
  достижение — явное событие: строка в журнале и отметка «индекс неполон» в отчёте, а не тишина.
- **Признак усечения.** Ответ, в котором строк ровно `limit`, считается обрезанным: обход продолжается
  с `page`/`resumeKey`, а не «заканчивается успешно».
- **`matchType` явно.** По умолчанию `domain` (нужны поддомены), при 504 — откат на `prefix` с записью
  в журнал: на `nginx.org` это разница между «нет ответа» и 50 000 адресов за 32 с.
- **Водяной знак.** Время старта инвентаризации пишется в инвентарь; все доборы идут с `from=<знак>`,
  итоговая сверка — с `to=<знак>`; так «полнота» проверяема, а не декларативна.
- **Добор на загрузке — по дешёвому запросу** (`from=водяной знак`, `collapse`, `limit` небольшой):
  это единицы-десятки строк, а не полный обход.
- **Добор на сборке — по ссылкам, а не по индексу.** На этапе сборки уже известны цели ссылок: если цель
  отсутствует в копии и её нет в очереди, адрес добавляется (в пределах `--rescue-limit`), скачивается и
  страница пересобирается. Это ловит то, чего в индексе может не быть вовсе (например, адреса,
  склеенные из относительных ссылок), и стоит одного прохода по уже прочитанным страницам.

Порядок важен: на сборке добор идёт **до** проверки ссылок, иначе отчёт зафиксирует битые ссылки, которые
через секунду перестанут быть битыми.

## 4. Что показывать пользователю

| Место | Что |
|---|---|
| журнал, инвентаризация | «индекс: страниц N из M, адресов K, обрезан/полон» |
| журнал, добор | «добрано из индекса на ходу: +X адресов»; «добрано по ссылкам при сборке: +Y» |
| отчёт, раздел «Полнота индекса» | адресов в индексе, попало в копию, категории расхождений: нет снимка / не скачано (лимит) / ошибка загрузки / не страница / не в индексе |
| итог CLI | поля `index_total`, `index_pages`, `index_truncated`, `added_live`, `added_build` |

## 5. Проверяемость (что и как мерить)

| Проверка | Стенд | Ожидание |
|---|---|---|
| Усечение | `nginx.org` (70 291 адрес) | при `--index-max-pages 200` в журнале «индекс обрезан: 200 из 98 страниц» — нет, страниц меньше; взять `lenta.ru`: «200 из 5401», отметка в отчёте |
| Полнота обхода | `prokupol.ru` | сумма по страницам = 1 638 = ответ без `limit` |
| Добор на загрузке | домен, у которого адрес появился в архиве после старта | адрес попадает в копию в том же прогоне, счётчик `added_live` = 1 |
| Добор на сборке | зеркало со ссылкой на отсутствующий файл, который есть в индексе | файл скачан, страница пересобрана, `added_build` = 1 |
| Отказ индекса | подмена ответа на 503 | повтор, затем отметка «индекс не получен»; пустой инвентарь не принимается за норму |
| Водяной знак | два прогона подряд | второй не перекачивает и не добавляет уже известное |

## 6. Риски

| Риск | Мера |
|---|---|
| Полный обход крупного домена долго (5 401 страница) | обход идёт параллельно загрузке и прерывается по времени/лимиту; предел — параметр, а не константа |
| 503/504 на обходе | повторы с паузой, откат `domain → prefix`, признак неполноты вместо тишины |
| Добор на сборке зацикливается (страница ссылается на себя) | бюджет `--rescue-limit` и запрет повторной постановки того же адреса |
| Копия меняется на ходу | пересборка только затронутых страниц, журнал сборки инвалидируется по затронутым путям |
| Индекс живёт | водяной знак `to=` для сверки; «полнота» считается на момент старта |

# Релизы: что, как и по каким правилам

Документ фиксирует одну схему. Всё, что ему противоречит в CI, README или
лендинге, — ошибка, а не альтернатива.

## Что выпускаем

Одна реализация — Rust. В релиз попадают шесть бинарников и Linux-бандл:

| Файл | Откуда | Лимит размера |
|---|---|---|
| `SiteRestorer-windows-x64.exe` | `cargo build --release`, target `x86_64-pc-windows-msvc`, `+crt-static` | 45 МБ |
| `SiteRestorer-windows-x64-cli.exe` | `--no-default-features`, `x86_64-pc-windows-msvc` | 15 МБ |
| `SiteRestorer-linux-x64-gui` | features `gui`, target `x86_64-unknown-linux-gnu` | 45 МБ |
| `SiteRestorer-linux-x64-cli` | `--no-default-features`, `x86_64-unknown-linux-musl`, статический | 15 МБ |
| `SiteRestorer-linux-x64.tar.gz` | оба Linux-бинарника + `.desktop`, иконка, `install.sh`, `README.txt` | — |
| `SHA256SUMS.txt` | контрольные суммы всех файлов | — |

Python и Go не собираются и не публикуются: `legacy/python` и `ports/go` —
архив исходников.

## Как называем

Схема: `SiteRestorer-<os>-<arch>[-cli][.exe]`.

- `<os>` — `windows` или `linux`; `<arch>` — `x64` (32-битных сборок нет с 3.6.1);
- `-cli` — только консольная сборка, без него — окно;
- `.exe` — только Windows;
- версии в имени **нет**: ссылки `releases/latest/download/<имя>` должны жить
  между релизами.

Версию видно в `--version`, в первой строке журнала окна, в `CHANGELOG.md`
и в названии тега. Внутри `tar.gz` лежит каталог `site-restorer-linux-x64`,
установщик ставит команды `site-restorer` и `site-restorer-gui`.

## Нумерация версий

- SemVer `MAJOR.MINOR.PATCH`, тег — `vX.Y.Z`.
- Единственный источник версии — `version` в `Cargo.toml`; CI падает, если тег
  ей не равен.
- `PATCH` — исправления и внутренние улучшения без новых возможностей.
- `MINOR` — новые возможности, совместимые с прежними.
- `MAJOR` — несовместимые изменения интерфейса, CLI или формата результата.
- Предрелизы — `vX.Y.Z-rc.N`: собираются тем же пайплайном, но не помечаются
  как latest и не обновляют ссылки на лендинге.

## Как собираем

- Только из тега: `on: push: tags: ["v*"]`. Ветка `main` собирает бинарники,
  но не публикует релиз.
- Версия тулчейна закреплена в `rust-toolchain.toml` (1.99.1) и в CI — так
  релиз не зависит от того, какой stable попал на раннер. Обновление тулчейна —
  отдельный коммит с прогоном всех гейтов.
- Профиль релиза: `opt-level = "z"`, LTO, `panic = "abort"`, `strip = "symbols"`;
  Windows — статический CRT (`+crt-static`), чтобы не требовать
  Visual C++ Redistributable.
- Перед сборкой обязательны гейты: `fmt`, `clippy -D warnings` (CLI и GUI),
  `nextest`, `audit`, `deny`, `machete`, `typos`.
- Каждый бинарник после сборки проверяется: `--version` печатает версию
  из `Cargo.toml`, размер не превышает лимит из таблицы.
- Контрольные суммы считаются в джобе релиза по фактическим файлам.
- Релиз-ноты берутся **из `CHANGELOG.md`** (секция `## <версия>`), а не из
  списка коммитов.

Текст ставит отдельный шаг через `gh release edit --notes-file`: у `softprops/action-gh-release`
пустой `body` (и нечитаемый относительный `body_path`) молча оставляет прежний текст релиза,
поэтому заметить ошибку в нотах можно только на странице релиза.

## Порядок выпуска

1. Изменения в `main`, гейты зелёные.
2. Запись в `CHANGELOG.md` — новая секция `## X.Y.Z — ГГГГ-ММ-ДД`.
3. `version` в `Cargo.toml` = X.Y.Z.
4. Локально: `cargo fmt --check`, `clippy -D warnings`, `nextest run`.
5. Коммит `chore(release): X.Y.Z`.
6. `git tag -a vX.Y.Z -m "..." && git push origin main vX.Y.Z`.
7. CI: гейты → сборки → релиз. Проверить, что в релизе ровно 7 файлов (32-битных нет с 3.6.1)
   и размеры совпадают с таблицей.
8. Обновить размеры в `README.md` и `BUILD.md`, если они изменились; лендинг
   правится только при смене имён файлов (сейчас имена стабильны).

## Что делать при ошибке в релизе

- Тег перевешивать можно только до того, как релиз кто-то скачал: удалить тег
  и релиз, исправить, поставить заново.
- После скачиваний — выпускать `PATCH` следом, старый релиз не переписывать.
- Удалять ассеты прошлых версий нельзя: на них могут ссылаться.

## Проверка релиза

```bash
gh release view vX.Y.Z --json assets --jq '.assets[].name'   # ровно 9 имён (ПЛ-11: с SBOM)
curl -sL .../releases/download/vX.Y.Z/SHA256SUMS.txt          # суммы на месте
./SiteRestorer-windows-x64.exe --version                      # версия совпадает
sha256sum -c SHA256SUMS.txt                                   # сходится
```

### Проверки платформ (ТЗ 4.12, docs/PLATFORMS.md)

| Что | Как | Ожидание |
|---|---|---|
| Манифест Windows | `mt.exe -nologo -inputresource:SiteRestorer-windows-x64.exe`;#1 -out:m.xml` и поиск `longPathAware`, `PerMonitorV2`, `asInvoker` | все три значения на месте (ПЛ-7) |
| Подсистема оконной сборки | `dumpbin /headers` → `subsystem` | `2 (Windows GUI)`; у консольной — `3` |
| Статический CRT | `dumpbin /dependents` | нет `VCRUNTIME140`, `MSVCP140`, `api-ms-win-crt-*` (ПЛ-7) |
| Пол glibc | `objdump -T SiteRestorer-linux-x64-gui \| grep -oE 'GLIBC_2\.[0-9]+' \| sort -Vu \| tail -1` | не выше `2.28` (ПЛ-6); до Д-58 показывает 2.39 |
| Базовая ISA | проверить `RUSTFLAGS` матрицы и `.cargo/config.toml` | `-C target-cpu=x86-64`, нет `native`/`v2`/`avx` (ПЛ-3, ПЛ-4) |
| SBOM | файл `SBOM-site-restorer.cdx.json` в ассетах, компонент больше нуля | приложен и входит в суммы (ПЛ-11) |
| Отладочные символы | артефакты `pdb-*` в сборке, в релизе `.pdb` нет | символы архивируются, но не поставляются (ПЛ-9) |

Проверки манифеста, glibc и пола выполняются в конвейере автоматически; таблица
нужна для ручной проверки после публикации и при разборе жалоб «не запускается».

### Если файл не запускается у пользователя

1. Спросить вывод `--version` в консоли: он работает даже при проблемах с окном.
2. Ошибка 14001 («параллельная конфигурация неверна») — повреждён или неверен
   манифест: пересобрать, проверить `assemblyIdentity` (версия четырьмя числами).
3. Сообщение про OpenGL — графический бэкенд (ПЛ-13, пункт Д-60): пока GUI на
   glow, в среде без OpenGL 3.3 окно не откроется, нужен консольный режим.
4. `GLIBC_2.xx not found` — сборка не уложилась в пол 2.28 (ПЛ-6, пункт Д-58).

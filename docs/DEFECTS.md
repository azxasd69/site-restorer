# Реестр дефектов Site Restorer

**Что это.** Учёт дефектов продукта Site Restorer (Rust + egui, MIT): по каждому — проявление, причина, принятое решение и способ проверки. Читатели: разработчик, ведущий выпуск, тот, кто решает вопрос о готовности версии.

**Область и границы.** Записи ОШ-1…ОШ-6 составлены по отчёту о проверке версии 3.3.0 на шести сайтах — [plans/2026-11-copy-verify-report.md](../plans/2026-11-copy-verify-report.md), раздел 5. Критерии приёмки — `TZ.md` §8.1 (ПРМ-1…ПРМ-13), признаки дефекта — §8.2, порядок устранения — §8.3. Каждый дефект привязан к критерию приёмки или пункту §8.2. Отчёт описывает один цикл проверки; дефекты из тестов, ревью и сообщений пользователей попадают сюда по тем же правилам.

**Версия и дата.** 1.4 — 11.11.2026. Продукт 3.5.0: ОШ-11…ОШ-13 исправлены (свежесть и полнота
копии), см. записи ниже. Продукт 3.4.0 (ускорение сборки; дефекты ОШ-7…ОШ-10 найдены ревью и живыми прогонами при доработке). ОШ-11…ОШ-13 найдены при разборе свежести копии ([plans/2026-11-snapshot-freshness.md](../plans/2026-11-snapshot-freshness.md), [docs/snapshots.md](snapshots.md)); исправление — 3.5.0.

## ОШ-1. Подсказка при отсутствии OpenGL 2.0 называет несуществующий файл

**Проявление.** В Windows-ВМ (Hyper-V без GPU) окно не открывается: «Не удалось открыть окно. egui_glow: OpenGL: egui_glow requires opengl 2.0+». Об ограничении среды программа сообщает правильно, но предлагает сборку `SiteRestorer-rust-win-cli-*.exe` — такого файла в релизе нет. Ассеты называются `SiteRestorer-windows-x86-cli.exe` и `SiteRestorer-windows-x64-cli.exe`; переименование выполнено в 3.1.3, текст подсказки остался старым. Источник: `src/main.rs:219` (английский текст), `src/main.rs:223` (русский).

**Воспроизведение.**
1. Запустить `SiteRestorer-windows-x86.exe` в ВМ без OpenGL 2.0.
2. Прочитать текст подсказки.

Ожидается имя файла, присутствующего в релизе; в 3.3.0 указано отсутствующее.

**Причина.** Имя файла записано литералом в двух языковых ветках и не сверяется с составом релиза; при переименовании ассетов в 3.1.3 обновлены не были.

**Решение.** В 3.3.1 имя консольной сборки берётся из одной функции `cli_build_name()` и зависит от платформы и архитектуры: на x64 — `SiteRestorer-windows-x64-cli.exe`, на x86 — `SiteRestorer-windows-x86-cli.exe`, на Linux — `SiteRestorer-linux-x64-cli`.

**Проверка.** Повторить воспроизведение на обеих архитектурах: подсказка называет сборку своей архитектуры, оба имени есть в ассетах релиза 3.3.1. Проверяются обе языковые ветки.

**Остаточный риск.** Автоматической сверки текста с составом релиза нет; имена живут в одной функции, но проверяются глазами.

## ОШ-7. Очистка прошлой копии не работает на длинных путях

**Проявление.** Копия архива собиралась в каталог, где глубина путей доходила до 260+ символов
(`parts/1-56 (Maruichi)/05413/...`). Перед полной сборкой программа пытается удалить прошлую
копию. Файлы оставались, и в отчёт попадали страницы, которых в новой сборке нет: на копии
centr-58 число файлов было 400 при 397 фактически скачанных, а счётчик «под видом страницы
не страница» показывал 0 при наличии PNG под именем `index.html`.

**Причина.** `fs::remove_dir_all` останавливается на пределе длины пути Windows и оставляет
часть дерева; ошибка игнорировалась (`let _ =`). Дополнительно префикс длинного пути `\\?\`
применялся к относительному пути вывода (`SiteRestore\site`), а такая форма не работает.

**Решение.** Удаление своим обходом с префиксом `\\?\` (`remove_tree`), каталог вывода
приводится к абсолютному пути в `Engine::new`, удаление осиротевших файлов идёт через
`long_path`. Ошибки удаления больше не скрываются молча.

**Проверка.** Прогон centr-58 (400 адресов): в копии ровно 400 файлов, 396 страниц, PNG под
именем страницы считается один раз (`foreign=1`), дерево после второго прогона побайтово
совпадает с первым.

## ОШ-8. Журнал повторной сборки всегда читался пустым

**Проявление.** Инкрементальная сборка не работала: каждый прогон пересобирал копию целиком,
строка «сборка: без изменений N» не появлялась.

**Причина.** В журнале `data/build.jsonl` числа пишутся без кавычек (`"size":1997`), а разбор
искал их как строки (`"size":"`), поэтому каждая строка отбрасывалась и карта оставалась пустой.
Дополнительно каталог `data` мог отсутствовать при сборке без загрузки — журнал молча не
сохранялся.

**Решение.** Отдельный разбор числовых полей (`json_number`), создание каталога `data` перед
записью, метка формата `#journal <формат> <версия> <хост>` в первой строке — журнал другой
версии или другого сайта не применяется.

**Проверка.** Тест `journal_survives_round_trip`, тест `journal_of_another_version_forces_full_build`,
живой прогон: второй прогон centr-58 даёт «без изменений 400, обновлено 0» и сборку за 0,02 с.

## ОШ-9. Ошибки записи файлов не видны

**Проявление.** При нехватке места или занятом файле страница попадала в счётчики и в журнал
сборки, хотя на диске её не было: отчёт показывал файлы, которых нет.

**Причина.** `fs::write` и `fs::copy` вызывались с игнорированием результата, а `pages`
увеличивался до записи.

**Решение.** Счётчики и запись журнала — только после успешной записи; первые десять ошибок
попадают в журнал работы строкой «не удалось записать <файл>: <причина>».

**Проверка.** Тест `second_build_skips_unchanged_files` (файл не переписывается), разбор кода
ревью; живой прогон на копии с недоступным каталогом даёт строку об ошибке и не считает файл
собранным.

## ОШ-10. Подписи карточки прогресса не соответствуют этапу

**Проявление.** На этапе сборки карточка называлась «Скачано» и показывала «1638 / 1638»,
рядом стояла «Скорость 0 KB/s»: пользователь не понимал, идёт ли ещё работа.

**Причина.** Подписи были одни на все этапы, значения брались из счётчиков загрузки.

**Решение.** На этапах сборки и проверки — «Обработано N / M» и файлов в секунду; «Скачано»
и «Скорость» остаются только на загрузке. Строки журнала с ошибками движка окрашиваются как
предупреждения.

**Проверка.** Снимок окна на этапе сборки: подписи «Обработано» и «файлов/с», значения меняются
по ходу сборки.

## ОШ-2. Адрес архива зашит как `http://`, попытки `https` нет

**Проявление.** В сети проверки порт 80 до `web.archive.org` перестал отвечать: с хоста `http://web.archive.org/` → код 000, `https://` → 200 (с внешнего сервера отвечали оба). Программа падала на инвентаризации:

```
[  4.0%] inventory  CDX: страница 1 из 2
CDX: страница 1 — ошибка io: Connection refused (os error 111)
ошибка: archive unavailable
```

Так упали пять прогонов подряд — bali58, rustorgshina58, centr-58 и повторные.

**Воспроизведение.**
1. Закрыть исходящий 80 до `web.archive.org`, оставив 443 открытым.
2. Запустить прогон любого адреса.

Ожидается работа через `https`; в 3.3.0 — код 1 и «archive unavailable». Обход в тесте: закрепление рабочего адреса в `/etc/hosts` и в `hosts`.

**Причина.** Схема зашита в константе: `src/core.rs:510` — `agent_archive: "http://web.archive.org"`; тот же адрес использует `cdx_query` (`src/core.rs:648`). При недоступности 80-го порта вторая схема не пробуется, отказ выходит на `src/core.rs:928`.

**Решение.** В 3.3.1 — перебор схем `https` → `http` с запоминанием рабочей.

**Проверка.** Повторить прогон в той же сети при закрытом 80-м порте: страницы CDX читаются по `https`, сообщения «archive unavailable» нет. Обратный случай: при закрытом 443 программа переходит на `http` и прогон завершается кодом 0.

**Остаточный риск.** Полная недоступность обеих схем выбором схемы не покрывается — поведение в этом случае описано в ОШ-3.

## ОШ-3. При отказе архива нет нарастающих повторов и продолжения

**Проявление.** При недоступности архива прогон завершается кодом 1: каталог копии остаётся пустым (8 КБ), в журнале одна строка об ошибке. Повторы есть только транспортные — три попытки с паузой 5 с, — после них выход без сохранения сделанного. Для сайтов в тысячи адресов это потеря всей работы при кратком сбое сети.

**Воспроизведение.**
1. Закрыть доступ к архиву (оба порта).
2. Запустить прогон сайта с несколькими тысячами адресов, дождаться исчерпания повторов.

Ожидается либо продолжение с места остановки, либо сохранённая часть копии; в 3.3.0 — код 1 и пустой каталог.

**Причина.** Повтор ограничен тремя попытками с фиксированной паузой; отказ на этапе инвентаризации считается окончательным, частичный результат не сохраняется.

**Решение.** В 3.3.1 — нарастающие паузы между попытками и попытка второй схемы (см. ОШ-2).

**Проверка.** Кратковременный обрыв доступа к архиву во время инвентаризации: прогон дожидается восстановления связи, продолжает работу и завершается кодом 0. Длительный отказ: в журнале видны попытки с растущими паузами, сообщение об отказе читаемо, код возврата не 0.

**Остаточный риск.** Продолжение с места остановки в 3.3.1 не реализовано: при долгом отказе прогон по-прежнему заканчивается без сохранения части работы. Это отдельная доработка, а не исправление данного дефекта.

## ОШ-4. Windows-прогон завис на welcome2penza: 25 минут без записей и вывода

**Проявление.** Windows-прогон welcome2penza не завершился за 25 минут: скачано 5 358 файлов (486 МБ), последняя запись в 00:58; к 01:23 — ни новых файлов, ни строк журнала, процесс жив (CPU 14 с, 27 потоков). Файл журнала за всё время — 0 байт, содержимое (68 КБ) появилось только при завершении процесса. На Linux тот же сайт шёл с построчным выводом прогресса. То же поведение делает прогон неуправляемым по журналу.

**Воспроизведение.** Не воспроизведено: один случай на 12 прогонов (11 завершились кодом 0). Повторный запуск welcome2penza в Windows-ВМ зависание не повторил, причина не установлена.

**Причина.** Не установлена. Данных для вывода о причине отчёт не содержит; связь с объёмом копии или с платформой не доказана — на Linux тот же сайт шёл нормально.

**Решение.** В 3.3.1 — только наблюдаемость: строки прогресса сбрасывают буфер вывода сразу, поэтому журнал при перенаправлении в файл растёт во время работы. Поведение загрузки не менялось.

**Проверка.** Выполнена на 3.3.1: прогон с перенаправлением вывода в файл — размер журнала растёт на ходу (59 → 176 → 265 байт за 10 секунд, первая строка видна сразу). Проверка подтверждает наблюдаемость, а не устранение зависания.

**Остаточный риск.** Причина не найдена, зависание может повториться на другом сайте. Статус «не подтверждён»: дефект остаётся открытым для диагностики и не считается исправленным.

## ОШ-5. Ответ не проверяется по типу: PNG сохранён как страница `index.html`

**Проявление.** В копии centr-58 пути `clamps_catalog?limit=40` и `.abcp-show-bimg/…` содержали не HTML, а PNG (`\x89PNG` в первых байтах), но были сохранены как страница `index.html`. В `data/inventory.jsonl` у обоих `"mime": "text/html"`, в отчёте они считались страницами. Итог: «страницы» без текста, число страниц завышено.

**Воспроизведение.**
1. Скачать `https://centr-58.ru/` с лимитом 400 (как в отчёте).
2. Открыть `clamps_catalog?limit=40/index.html` и `.abcp-show-bimg/…/index.html` в копии.

Ожидается картинка или запись в ошибках; в 3.3.0 — файл с расширением `.html` и содержимым PNG.

**Причина.** Фактический тип ответа не сверяется с ожидаемым: тип берётся из адреса, а не из содержимого, поэтому поле `mime` в инвентаре повторяет ожидание и не отражает ответ.

**Решение.** В 3.3.1 содержимое проверяется по сигнатуре до учёта в отчёте: файл остаётся по тому же пути (ссылки на него не ломаются), но страницей не считается; в журнал идёт до трёх примеров, в отчёт — строка «Под видом страницы не страница».

**Проверка.** Выполнена на 3.3.1: прогон centr-58 с лимитом 400 дал `foreign=1`, страниц 393 (без 3 ненайденных адресов), в отчёте строка «Под видом страницы не страница: 1», в готовой копии ровно один `.html` с сигнатурой PNG. В 3.3.0 таких файлов было два (второй адрес в новом прогоне отдал другое содержимое — поведение архива, не программы).

**Остаточный риск.** Имя файла в копии остаётся `index.html`: браузер покажет картинку, а не 404, но по имени файл выглядит страницей. Переименование по фактическому типу потребовало бы пересчёта ссылок и сделано не было сознательно. Сигнатура различает не все форматы — для остальных тип остаётся по ожиданию.

## ОШ-6. RESULT и отчёт расходятся с содержимым папки `site/`

**Проявление.** На rustorgshina58 итог прогона — `RESULT {"ok":400,"total":400,"pages":1}`, при этом в `site/` лежит 150 файлов (1 html, 71 js, 35 css, 43 картинки). Отчёт по типам: HTML 3/3, CSS-JS 291/291, IMG 106/106. То есть 400 адресов скачаны, но в готовой копии 150 файлов. Поведение одинаково на Linux и Windows.

**Воспроизведение.**
1. Скачать `https://xn--58-6kclz4aepbilk4e.xn--p1ai/` с лимитом 400.
2. Сравнить число файлов в `site/` с числом в строке `RESULT` и в отчёте.

Ожидается совпадение чисел; в 3.3.0 — 400 в отчёте против 150 в папке.

**Причина.** Число скачанных считает **адреса**, а не файлы: 400 адресов дают 150 уникальных путей (`index.html` — три адреса, `bitrix/js/main/core/core.js` — три и т. д.), потому что варианты с параметрами и повторы адреса укладываются в тот же путь и перезаписывают тот же файл. Сборка копирует все файлы зеркала — отбора «только по ссылкам» нет; расходились не файлы, а два разных показателя, и нигде это не было сказано.

**Решение.** В 3.3.1 итог и отчёт показывают оба числа: адреса и файлы, плюс файлы зеркала и уникальные пути, с пояснением о причине разницы.

**Проверка.** Выполнена на 3.3.1: `RESULT {"ok":400,"total":400,"files":150,"mirror":150,"unique":150,…}`; в отчёте карточка «Файлов в копии: 150», строки «Файлов в зеркале», «Уникальных путей в инвентаре» и пояснение; пересчёт папки `site/` даёт те же 150.

**Остаточный риск.** Показателей стало больше (адреса, файлы копии, файлы зеркала, уникальные пути) — читателю нужно пояснение, которое теперь есть в отчёте, но не в справке CLI.

## Наблюдения без приговора

Замечания из отчёта, у которых нет нарушенной нормы §8.2 или критерия ПРМ. Дефектами не являются; при появлении требования или критерия переводятся в записи Д-N.

1. **Частичные копии дают десятки тысяч «битых» ссылок.** При лимите 800 у bali58 в отчёте 76 653 битых ссылки — это адреса страниц, которые есть в архиве, но не скачаны из-за лимита. Отличить «нет в архиве» от «не скачано по лимиту» отчёт не позволяет.
2. **Ссылки переписываются только на существующие файлы.** Если файла в зеркале нет, ссылка остаётся абсолютной: на `404/index.html` в Windows-копии осталась `href="/assets/css/header.css?1740641601"`, в Linux-копии переписана — потому что в её зеркале оказался нужный вариант файла. Поведение разумное; разница между копиями объясняется разными снимками, а не платформой.
3. **Кириллица в консоли Windows.** При выводе в терминал русский текст читается как «╨б╨║╨░╤З╨░╨╜╨╛»: консоль в cp866, программа пишет UTF-8. В файл пишется корректный UTF-8 — копия и журнал не страдают.

## Порядок пополнения

1. **Регистрация.** Дефект получает следующий свободный ID Д-N; пропуски в нумерации не заполняются. В записи сразу указываются проявление, воспроизведение, нарушенный критерий ПРМ-N или пункт §8.2 и серьёзность.
2. **Отсев.** Если нарушенная норма не называется — замечание идёт в «Наблюдения без приговора» с указанием, какого требования не хватает.
3. **Исправление.** Версия исправления фиксируется в записи и в `CHANGELOG.md` (§8.3). Дефекты классов «неверная кодировка», «абсолютные ссылки в копии», «неполный файл под итоговым именем» блокируют выпуск до устранения.
4. **Проверка.** Запись дополняется способом проверки с ожидаемым результатом; без выполненной проверки статус «закрыт» не ставится.
5. **Закрытие.** Закрытый дефект остаётся в сводной таблице со статусом и версией — история не удаляется. Переоткрытие — тот же ID со статусом «открыт» и новой датой.
6. **Сверка.** При подготовке релиза таблица сверяется с `CHANGELOG.md` и с `PLAN.md` §4 «Реестр доработок»: одна и та же работа не должна числиться и дефектом, и доработкой.

## ОШ-11. Один путь копии — несколько адресов, версия не выбирается

**Проявление.** В копии оказывается один файл там, где архив отдал два адреса: `/api/` (2015)
и `/api/index.html` (2016) дают `api/index.html`. Какой снимок останется — зависит от порядка
потоков. На `011.vuejs.org` 12 адресов дали 11 файлов, на домене `rustorg` 400 адресов — 150 файлов.

**Причина.** После отбора по адресу (`best` по нормализованному адресу, `src/core.rs:1097-1112`)
элементы не дедуплицируются по локальному пути: `paths::url_to_local_path` отбрасывает хост и
приводит каталог к `index.html`, поэтому два элемента пишут один файл. Проверка «файл уже есть»
стоит в начале загрузки и при нескольких потоках не спасает.

**Решение (3.5.0).** Дедупликация по пути до загрузки; остаётся адрес с самым свежим снимком
(при равенстве — адрес каталога); остальные не скачиваются, счётчик `path_collisions` в отчёте.
Правило — [docs/snapshots.md](snapshots.md) §9.

**Проверка (выполнена 11.11.2026).** `011.vuejs.org`: 12 адресов, перезаписей путей 3, повторные
прогоны дают тот же файл; `nginx.org`: перезаписей 10; сумма «файлы + перезаписи» равна числу
адресов индекса (ПРМ-18).

## ОШ-12. Поддомены в одном дереве копии

**Проявление.** Домен с рабочими поддоменами (`mail.x…`, `mta-sts.x…`, `mx.x…`) собирается в одну
папку: три разных `index.html` претендуют на один файл, в копии остаётся страница одного из них.

**Причина.** `paths::url_to_local_path` (`src/paths.rs:91-121`) строит путь только из пути адреса;
хост не участвует, поэтому страницы разных хостов совпадают.

**Решение (3.5.0).** Для всех хостов, кроме основного, путь включает хост: `mail.example.com/index.html`.
При одном хосте дерево копии не меняется. Ссылки на поддомены переписываются в эти папки.

**Проверка (выполнена 11.11.2026).** Путь поддомена включает хост (`mail.example.com/index.html`);
копия однохостового домена (`011.vuejs.org`, `nginx.org`) дерево не изменила — совпадает с 3.4.0.

## ОШ-13. В копию попадает самый ранний снимок адреса

**Проявление.** Копия `011.vuejs.org` собрана из снимков 2015 года, хотя в архиве есть 2025–2026;
`nginx.org` — из снимков 2008–2015 при наличии снимка 10.11.2026.

**Причина.** Список адресов запрашивается с `collapse=urlkey`: архив оставляет первую запись
в порядке «urlkey, время», то есть самый старый снимок. Отпечаток из индекса подставляется
в адрес воспроизведения, поэтому архив отдаёт именно этот старый снимок.

**Решение (3.5.0).** Целевая дата воспроизведения — текущее время (режим `newest`), режимы
`oldest` и `--as-of` для воспроизводимости; фактическая дата снимка читается из `Memento-Datetime`
и попадает в журнал и отчёт; при непригодном свежем снимке — добор к более старым.
Правила — [docs/snapshots.md](snapshots.md) §4–§6.

**Проверка (выполнена 11.11.2026).** `011.vuejs.org`, режим `newest`: `/` — снимок 15.11.2025, `js/vue.min.js` — 22.10.2026;
`oldest` — 01.11.2015 (как 3.4.0); в отчёте указан год каждого снимка (ПРМ-17).

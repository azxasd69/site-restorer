# Платформы, базовая ISA и воспроизводимость сборки

Документ фиксирует требования владельца к набору платформ, к качеству сборки и к
составу поставки. Он дополняет ТЗ (раздел 4.12) и План (пункты Д-57…Д-63), а
также проверки выпуска (docs/RELEASE.md).

Дата ввода: 12.11.2026. Основание: требования владельца, переданные одним пакетом.

---

3.6.0, и ссылка ведёт в её релиз по тегу, а не на `latest`.

## 2. Базовая ISA

- x86-64 фиксируется явно: `-C target-cpu=x86-64` (SSE2). Значение задано и в
  `.cargo/config.toml` (локальная сборка), и в `RUSTFLAGS` матрицы конвейера —
  потому что переменная окружения **полностью перекрывает** настройку из файла,
  а не дополняет её.
- Запрещено в репозитории, конвейере и любой `RUSTFLAGS`: `target-cpu=native`,
  `x86-64-v2/v3/v4`, глобальные `+avx,+avx2,+fma,+sse4.*`.
- Ускорения — только runtime dispatch с обязательным скалярным путём и тестом на
  совпадение результатов; проверка возможностей кэшируется (`OnceLock`), а не
  выполняется на каждый вызов. AVX-512 в обязательный путь не вводится.
- Текущее состояние: собственного SIMD-кода в проекте нет; требование
  действует как запрет и как правило на будущее.

### 2.1 Проверено: пин не меняет машинный код

Собраны две сборки одного коммита (профиль без отладочной информации, только
`-C target-cpu=x86-64` как различие). Секция `.text` совпала байт в байт
(2 713 600 байт, одинаковый SHA-256), в `.rdata` различаются 22 байта — метки
времени сборки. Вывод: для `x86_64-*` пин равен умолчанию rustc, его ценность —
контракт и воспроизводимость, а не скорость.

### 2.2 Контракт на ускорения

Любой `unsafe`-путь ради скорости обязан иметь:

1. скалярного двойника, который остаётся умолчанием;
2. проверку возможностей во время работы через `isa::caps()` (`OnceLock`), но не
   `cfg!(target_feature = …)` — это проверка при компиляции, при базовой ISA она
   всегда ложна;
3. тест побайтового совпадения результата с двойником, включая границы (пустое
   тело, обрыв на границе буфера, экранирование);
4. выключатель `SR_NO_SIMD=1`, с которым набор тестов проходит полностью;
5. строку о выбранном пути в отчёте и в `--version --verbose`.

### 2.4 Что проверка не покрывает (осознанные границы)

`scripts/check-flags.py` разбирает конвейер **по строкам**, без YAML-парсера:
это дешёво и не тянет зависимостей, но у него есть границы, которые надо
помнить при правках:

- задача узнаётся по ключу с отступом в два пробела; нестандартное оформление
  (многострочные ключи, `jobs` в include) проверка не увидит;
- освобождение для `x86-64-v3` привязано к задаче `isa-bench` **и** к наличию в
  ней замера (`bench_`), но подделать такую задачу в своём файле технически
  можно — от этого защищает обзор, а не скрипт;
- проверка видит только репозиторий: локальные `RUSTFLAGS` разработчика она не
  контролирует (там спасает то, что файл — единственный источник в конвейере).

Долги, зафиксированные на будущее (Д-70):

- `Avx2`-пропуск пока не имеет потребителей: ускоренных путей нет, `SR_NO_SIMD`
  влияет только на строку отчёта. Первый реальный потребитель появится вместе с
  первым `#[target_feature]`;
- разбор конвейера по строкам стоит заменить на YAML-разбор, если правок в
  конвейере станет больше;
- `normalize_url` в `fold_row` аллоцирует адрес до сравнения дат — это
  необходимо для поиска в карте, но остаётся копией на строку.

### 2.3 Решения владельца 12.11.2026

| Вопрос | Решение | Следствие |
|---|---|---|
| Своя проверка целостности копии (локальный SHA-256, SHA-NI) | **нет** | `sd`-ускорение не вводится; отпечаток по-прежнему берётся из CDX |
| Отдельная быстрая сборка `x86-64-v3` | **нет** | один бинарник на парк; имена ассетов релиза стабильны |
| Прекращение 32-битных сборок (Д-57) | **сразу** | матрица, нормы ПР-6, РЛ-12, сайт и документация приведены к 64-битным |

(«параллельная конфигурация неверна»); `build.rs` подставляет `3.5.2.0`.

## 4. Linux и пол glibc

Требование: собранное под glibc требует не выше **2.28** (RHEL 8, Debian 10),
проверка экспортируемых версий символов обязательна в конвейере.

Замер 12.11.2026 по выпущенному файлу `SiteRestorer-linux-x64-gui`:

```
objdump -T | grep -o 'GLIBC_[0-9.]*' | sort -Vu | tail -1
→ GLIBC_2.39
```

То есть текущая сборка **не запустится** на Ubuntu 20.04, Debian 11, RHEL 8.
Причина — сборка на `ubuntu-latest` (glibc 2.39). В конвейер добавлена
проверка «не выше 2.28»: до Д-58 она предупреждает (иначе выпуск 3.6.0 был бы
невозможен), после Д-58 включается строгий режим `GLIBC_FLOOR_STRICT=1`.
Ограничение зафиксировано в ТЗ как ОГ-11, чтобы оно не потерялось.

**Сделано 12.11.2026 (Д-58):** сборка linux-gnu идёт через `cargo-zigbuild` с
суффиксом `x86_64-unknown-linux-gnu.2.28`; проверка символов в конвейере переведена
в строгий режим (`GLIBC_FLOOR_STRICT=1`), то есть превышение пола ломает сборку,
а не выдаёт предупреждение. Запасной путь, если zigbuild подведёт, — контейнер
`quay.io/pypa/manylinux_2_28_x86_64`.

Замер после правки (первый зелёный прогон конвейера):
`максимальная требуемая версия glibc: GLIBC_2.28` — пол достигнут; там же проверка
защит ELF: `PIE, RELRO, BIND_NOW — на месте`.

Статический musl остаётся вариантом CLI по отдельному решению: он не зависит от
glibc вовсе, но требует отдельной проверки поведения (DNS, локали).

## 5. macOS

Требование: `x86_64-apple-darwin` + `aarch64-apple-darwin`, объединение `lipo`
в universal, `MACOSX_DEPLOYMENT_TARGET=11.0`, `.app`-бандл, `codesign
--options runtime --timestamp`, нотаризация `notarytool`, `stapler staple`,
распространение `.dmg`. Порядок: build → lipo → sign → notarize → staple.

Состояние: **не собирается**. Блокирует два обстоятельства, оба внешние для кода:
1. нет учётной записи Apple Developer (Developer ID Application) — без неё
   подпись и нотаризация невозможны, а неподписанный `.app` на macOS 15
   не запускается без ручного снятия карантина;
2. сборка возможна только на macOS-раннере (`macos-14`), то есть добавляет
   минуты конвейера и отдельную ветку упаковки.

Решение: работа вынесена в Д-59, выполняется при появлении сертификата.
До этого macOS не заявляется поддерживаемой (ТЗ, ОГ-9).

## 6. 32-битные сборки — прекращены 12.11.2026 (Д-57)

Было: требование «`i686-*` не выпускаются» расходилось с фактом — в матрице
жили две ячейки, дававшие `SiteRestorer-windows-x86.exe` и
`SiteRestorer-windows-x86-cli.exe`, и на них опирались нормы ПР-6 и
испытательный стенд Win10-x86.

Решение владельца 12.11.2026 — прекратить **сразу**. Сделано:

1. из матрицы убраны обе ячейки `i686-pc-windows-msvc`, упрощены условия
   Windows-шагов (проверка PE, публикация PDB);
2. ТЗ 2.19: из ПР-6 убраны нормы 35 МБ и 10 МБ, строка `РЛ-12` снята, ПЛ-2
   отмечено выполненным;
3. сайт: карточка x86 стала архивной и ведёт на `releases/download/v3.6.0/…`,
   требования к системе — только x64; в `scripts/check_downloads.py` добавлена
   проверка ссылок на конкретный тег (по релизу этого тега, а не по последнему);
4. документация: README, BUILD, PUBLISH, индексные страницы сайта.

Последствия, принятые осознанно: у пользователей 32-битной Windows остаётся
3.6.0 (файлы не удаляются), стенд Win10-x86 больше не нужен, из базовой ISA
уходит ветка `pentium4`.

| Требование | Состояние |

| Различия блокировок и прав не ломают логику | проверено на Windows и Linux (прогоны 11–12.11.2026) |

## 8. Графика

Требование: wgpu с разрешёнными fallback-бэкендами (DX12 / Vulkan / Metal / GL),
работа на программном рендере и в виртуальной машине, Wayland и X11 без
пересборки, per-monitor DPI и дробное масштабирование.

Состояние: GUI построен на **glow** (только OpenGL). Следствия уже наблюдались:
в Hyper-V без GPU окно не открывается с сообщением про OpenGL 2.0 (ОШ-1),
на macOS путь Metal недоступен в принципе.

Решение: Д-60 — перевод на `eframe` с признаком `wgpu`, проверка на Windows
(с GPU и в ВМ), X11/Wayland, программный рендер. 32-битные сборки прекращены
(§6), поэтому ограничение wgpu на i686 больше не учитывается.

## 9. Инструментарий и профиль релиза

| Требование | Состояние |
|---|---|
| `rust-toolchain.toml` с точной версией | выполняется: канал `1.99.1`, компоненты `clippy`, `rustfmt` |
| MSRV указан | **сделано 12.11.2026**: `rust-version = "1.88"` (Д-61), проверяется отдельной задачей конвейера |
| `Cargo.lock` в репозитории | выполняется |
| Профиль: `lto="thin"`, `codegen-units=1`, `opt-level=3` | **сделано 12.11.2026** (было `opt-level="z"`, `lto=true`) |
| `debug="line-tables-only"`, PDB/dSYM в архив, не в поставку | сделано: профиль включает строки, PDB уходит отдельным артефактом конвейера |

Замер перед сменой профиля (GUI, Windows x64): `opt-level="z"` + `lto=true` →
7,2 МБ; `opt-level=3` + `lto="thin"` + `debug="line-tables-only"` → 8,7 МБ.
Разница 1,5 МБ при норме ПР-6 45 МБ, поэтому принят профиль политики.
`panic="abort"` сохранён: он задан нормами и уменьшает размер, но означает, что
развёрнутых трассировок в поставке не будет — это известное ограничение.

| Требование | Состояние |

| Windows: Authenticode, проверка mitigations (`High Entropy VA`, `Dynamic base`, `NX compatible`, `Guard CF`) | **частично сделано 12.11.2026**: три защиты проверяются в конвейере (`dumpbin /headers`); CFG требует сборки всех объектов с `/guard:cf` — вторая часть Д-63; Authenticode ждёт сертификата |

`dumpbin /dependents` показывают `High Entropy Virtual Addresses`, `Dynamic base`,
`NX compatible`; `Guard CF` появляется только при `/guard:cf`, который для
MSVC-цели задаётся флагом линковки.

## 11. Что из этого уже сделано в 3.6.0

1. Манифест Windows (asInvoker, PerMonitorV2, longPathAware, supportedOS) —
   встроен в PE, проверено извлечением.
2. Базовая ISA зафиксирована в `.cargo/config.toml` — единственном источнике;
   конвейер `RUSTFLAGS` не передаёт (ПР-15).
3. Профиль релиза приведён к политике (замер до/после в §9).
4. SBOM в составе релиза и контрольных сумм.
5. Проверки в конвейере: наличие манифеста; PDB сохраняется отдельным
   артефактом. Пол glibc в 3.6.0 ещё предупреждал — строгим он стал после Д-58
   (§4).
6. Атомарная замена файла на Windows: при занятом имени старый файл удаляется
   перед `rename`.

# Скорость сборки копии: замеры и разбор (3.5.0 → 3.5.1)

**Стенд:** `rufence.ru` — 5394 файла в зеркале, 756 МБ; копия 760 МБ. Разметка: 3932 HTML на 694 МБ
(средняя страница 181 КБ, крупнейшая 716 КБ). Внутренних ссылок 1,44 млн, битых 109 тыс. (7,6 %).
Журнал сборки — 100 МБ на 5395 записей (18,6 КБ на запись: почти всё — цели ссылок).

**Машина:** 22 ядра, чтение 147 МБ/с, запись 30 МБ/с (запись упирается в проверку на лету).
Время мерилось пофазными таймерами в отдельной сборке (`SR_PROF=1`), сеть при замерах сборки
отключена (`SR_BENCH_INVENTORY`), иначе цифры смешиваются с ожиданием архива.

## Итог

| Сценарий | 3.5.0 | 3.5.1 | Ускорение |
|---|---|---|---|
| Полная сборка (журнала нет) | 105–112 с | 63 с | 1,7× |
| Повторная сборка (ничего не изменилось) | 36–40 с | 10,6 с | 3,6× |
| Реальный прогон с сетью | 552 с | 52,7 с | 10,5× |

Скорость полной сборки: 7,1 → 12,0 МБ/с при записи на диск 30 МБ/с. Теоретический предел на этой
машине — около 30 с (756 МБ чтения + 760 МБ записи), то есть запас ещё есть, но он требует
сокращать объём записи, а не код.

## Куда уходило время

### Полная сборка, 105 с → 63 с

| Фаза | 3.5.0 | 3.5.1 |
|---|---|---|
| обход зеркала (5394 файла) | 3,5 с | 0,3 с |
| индекс путей | 0,03 с | 0,01 с |
| **обработка файлов** | **91–105 с** | **63 с** |
| слияние журнала и уборка сирот | 4,3 с | 1,5 с |
| запись журнала (100 МБ) | 1,4 с | 1,3 с |
| проверка ссылок | 3,6 с | 0,12 с |

Внутри обработки (процессорное время, сумма по потокам):

| Операция | 3.5.0 | 3.5.1 |
|---|---|---|
| регулярные выражения | 2245 с | 497 с |
| чтение файлов | 5 с | 5 с |
| запись файлов | 23 с | 23 с |
| определение кодировки | 2,7 с | 1,7 с |

Отсюда главный вывод: в 3.5.0 сборка была **процессорной** (21 из 22 потоков заняты регулярками),
в 3.5.1 — **дисковой** (запись 725 МБ при 30 МБ/с).

### Причина №1: движок регулярных выражений

Проект использовал `regex-lite` — крейт без зависимостей и с маленьким бинарником. На шаблонах
переписывания ссылок он даёт **3,3–3,7 МБ/с**, а документ проходит четыре прохода (атрибуты,
`srcset`, `url()` в CSS, `<base>`), то есть 694 МБ сканируются 2,5 раза.

Замер на реальных страницах того же сайта:

| Движок | 716 КБ, замена | 171 КБ, замена |
|---|---|---|
| `regex-lite` 0.1 | 211 мс · 3,3 МБ/с | 51 мс · 3,3 МБ/с |
| `regex` 1.13 | 2,5 мс · **274 МБ/с** | 1,3 мс · **125 МБ/с** |

Разница — 40–80 раз. Цена: бинарник вырос с 6,2 до 7,0 МБ (+0,8 МБ) и сборка чуть дольше.
Копия сайта после замены сверена побайтово: 5396 файлов, различий нет.

### Причина №2: обход дерева с `stat` на каждый файл

`walk_files` вызывал `is_dir()` и `is_file()` — по два системных вызова на каждую запись
(5394 файла + 5931 каталог). 3,5 с. Данные о типе записи уже приходят вместе с содержимым
каталога: `DirEntry::file_type()` берёт их оттуда. Стало 0,3 с — **в 12 раз быстрее**, и это
касается всех обходов: зеркала, копии, уборки сирот, отчёта.

### Причина №3: лишние обходы и копии

- «Уборка» временных файлов обходила `mirror`, `site`, `out` и `data`, а `out` содержит первые три:
  дерево проходилось дважды (16 с). Теперь `mirror` и `data` — один раз, причём список зеркала
  уходит в сборку.
- Список файлов копии снимался дважды (уборка сирот и проверка). Теперь один раз, дальше кеш.
- Цели ссылок копировались при слиянии журнала (1,4 млн строк). Теперь `Arc<Vec<String>>`.
- Проверка ссылок строила `format!("{key}/index.html")` на каждую из 1,44 млн ссылок. Теперь
  множество каталогов считается заранее: 3,6 с → 0,12 с.

### Причина №4: сеть на повторных прогонах

Реальный прогон 3.5.0 занимал 552 с, хотя локальная работа — 40 с:

- **455 с** — добор по ссылкам: 500 целей, на каждую до шести запросов (цепочка старых снимков).
  При 109 тыс. битых ссылок это не даёт ничего. Теперь: бюджет 30 с (`--rescue-budget`), одна
  попытка на цель, и добор вообще не запускается, если в прогоне не появилось новых файлов.
- **60 с** — 26 адресов, которых нет на диске, запрашивались заново каждый прогон. Теперь они
  попадают в `data/no-snapshot.tsv` и не трогаются 7 дней (`--retry-missing`).

Остаток 52,7 с — это в основном ответ архива на список адресов (~40 с), наша часть ~10 с.

## Что осталось (кандидаты на следующий раз)

| Что | Стоимость сейчас | Что можно сделать |
|---|---|---|
| Журнал сборки: 100 МБ на прогон | 1,7 с чтение + 1,3 с запись | Хранить цели как 64-битные хеши: файл ~15 МБ. Минус: добор по ссылкам теряет адреса целей для уже собранных страниц |
| `stat` на каждый файл в загрузке и сборке | 1,1 с + ~1,5 с | Брать размер и время из того же `DirEntry::metadata` (на Windows без вызова) |
| Запись 725 МБ при 30 МБ/с | ~24 с | Не переписывать файлы, содержимое которых не изменилось (сравнение по хешу содержимого, а не по размеру и времени) |
| Четыре прохода по документу | ~497 с CPU | Один объединённый проход с предфильтрами; на дисковой машине выигрыша почти не даст |

## Как повторить

```powershell
# 1) измерительная сборка с таймерами (в продукт не входит)
#    в копии репозитория добавляются prof()/SR_PROF и режим SR_BENCH_INVENTORY
cargo build --release

# 2) полная сборка без сети
$env:SR_PROF='1'; $env:SR_BENCH_INVENTORY='<папка>\data\inventory.jsonl'; $env:SR_BENCH_NO_RESCUE='1'
site-restorer.exe --cli --site rufence.ru --out <папка>

# 3) сверка результата с эталоном
python scratch\cmp-size.py   # пути и размеры; побайтово — по манифесту SHA-256
```

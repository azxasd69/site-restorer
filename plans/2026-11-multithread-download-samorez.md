## 0. Главный вывод

1. **Реализованный алгоритм для цели «максимальная скорость скачивания» не оптимален.** При том что сама обработка уже скачанных файлов (`build` + `verify` + `report`) занимает **0,23–0,63 с** даже на `400` файлах, время скачивания на `samorez.pro` упирается не в ширину канала (9,42 МБ скачивались **48–231 с**), а в четыре архитектурных узких места внутри `3.6.5`:
   - **Пул keep-alive в `ureq 3.5.1` не настроен (`max_idle_connections_per_host = 3`)**: все `16–24` потоков ходят на один хост `web.archive.org`, поэтому соединения сверх `3` закрываются после каждого ответа и делают повторный TCP+TLS handshake (**1 615,7 мс** против **788,8 мс** на переиспользованном соединении — проигрыш **2,05×** по задержке на запрос в контрольном зонде).
   - **AIMD-контроллер (`Gate`) настроен на ложные снижения лимита на разноразмерных файлах**: уменьшает число слотов при `bps < prev_speed * 0.6` без единой ошибки `429` и игнорирует `503`/таймауты/`10061`; при этом `Win` начисляется только по завершении файла (не потоково), вызывая провалы скорости до `0 КБ/с` и ложные срабатывания регулятора.
   - **Инвентаризация (`inventory`) и добор по ссылкам (`rescue`) полностью однопоточны**, а фоновый `recheck` в конце `download()` задерживает выход после скачивания всех файлов (вплоть до `+8,9 с` в `exp-w2` и `+3,2 с` в `exp-w16`), если попал на границу `120 с`.
   - **На 8 потоках достигается оптимум для `web.archive.org` в текущей реализации (`51,01 с`, `2,92 ф/с`, `189,0 КБ/с`)**, тогда как дефолтные `16` потоков на длинном прогоне (`400` адресов) оказались **медленнее на 20 %** (`126,02 с` против `105,02 с` при `8`), а `24` потока на `150` адресах — **в 2,18× медленнее** (`111,02 с`, 2 таймаута).
2. **В релизе `3.6.5` выявлены два подтверждённых дефекта в контуре обрыва и отказоустойчивости:**
   - **`cleanup_temp()` не удаляет `.part`-файлы после обрыва** (`src/core.rs:2108-2130`, `src/core.rs:5945`): функция вызывает `walk_files_detailed()`, который сам же отфильтровывает `!is_temp_file(&path)`. Проверено опытом `exp-resume-pass3`: созданный `model.min.js.part` остался на диске (`PART_LEFT=True`).
   - **Переключение `https → http` при отказе соединения (`10061`) не срабатывает на русской Windows** (`src/core.rs:5651-5680`): `scheme_switch_worthwhile()` ищет только английские подстроки (`"connection refused"` и т.д.), а не код `10061`, хотя `explain_net()` (`src/core.rs:5684`) его распознаёт. В `exp-resume-pass3` при 8 ошибках `10061` переключение на `http` не произошло ни разу.

## 1. Архитектура алгоритма многопоточного скачивания (релиз `3.6.5`)

### 1.1 Участники и границы ответственности

Механизм загрузки сосредоточен в `src/core.rs` и опирается на клиент `ureq 3.5.1` (`rustls`, `flate2/zlib-rs`) и стандартные потоки `std::thread`:

| Компонент | Где в коде | Назначение |
|---|---|---|
| Конфигурация агентов | `src/core.rs:1539-1554` | Два экземпляра `ureq::Agent`: `agent` (файлы: `connect 15 с`, `recv_response 60 с`, `per_read 30 с`, без `recv_body`) и `agent_index` (индекс: плюс `recv_body 120 с`). Настройки пула соединений не переопределены |
| Ограничитель `Gate` | `src/core.rs:349-396` | `Mutex<GateState { limit, inflight }> + Condvar`; стартует с `MIN_THREADS = 2`, ограничивает число одновременно выполняемых `fetch_one()` сверху `MAX_THREADS = 24` |
| Пополняемая очередь `Queue` | `src/core.rs:402-481` | `Mutex<VecDeque<Item>> + Condvar + HashSet<String> seen + AtomicBool closed + AtomicUsize planned`. Обеспечивает работу без выхода воркеров при пополнении из `recheck` |
| Пул воркеров `handles` | `src/core.rs:3086-3099` | Ровно `self.workers` (`1..=64`, по умолчанию `DEFAULT_WORKERS = 16`, задаётся `--workers`) постоянно живущих потоков ОС |
| AIMD-контроллер | `src/core.rs:2889-2923` | Отдельный поток с циклом `sleep(3 с)`, меняет `gate.limit` по `win_bytes`, `win_files` и `win_429` |
| Фоновый добор `recheck` | `src/core.rs:2981-3084` | Отдельный поток, раз в `120 с` или каждые `500` `ok`-файлов запрашивает CDX с `from=watermark` и добавляет новые адреса в `Queue` |
| Поток прогресса | `src/core.rs:2925-2976` | Раз в `300 мс` читает атомарные счётчики и шлёт `Progress` в UI/CLI |
| Ограничитель темпа `rate_wait` | `src/core.rs:880-903` | Сериализует старт запросов всех потоков по общему слоту времени `rate_next` (`--rate <req/s>`) |
| Потоковая запись `save_body` | `src/core.rs:1198-1244` | Пишет ответ 200 чанками по 64 КБ во временный `<файл>.part`, хранит только первые `HEAD_BYTES = 4096` байт в памяти |
| Добор старых снимков | `src/core.rs:1032-1047`, `1300-1318` | Внутри `fetch_one()` (под удерживаемым слотом `Gate`): при 404 или непригодном снимке делает CDX-запрос `limit=-depth` (`DEFAULT_FALLBACK_DEPTH = 5`) и до 5 GET |
| Добор по ссылкам `rescue` | `src/core.rs:4690-4745` | После `build` + `verify` в **1 поток** (цикл `for key in missing`) догружает отсутствующие цели, ограничен `rescue_limit = 500` и `rescue_budget = 30 с` |

### 1.2 Схема работы конвейера скачивания

```
[inventory (1 поток, agent_index)]
        │  items (после limit_order, watermark)
        ▼
[order_interleaved] ── чередование типов html → code → img → other
        │
        ▼
[Queue::new(todo, already)] + mark_seen(все items)
        │
        ├──► [self.workers потоков (1..64)]
        │       └─ queue.pop() ─► gate.acquire() ─► fetch_one() ─► gate.release()
        │                                             ├─ проверка файла в mirror/ (>0 Б)
        │                                             ├─ дедупликация по digest (hard_link)
        │                                             ├─ attempt() → open() → save_body(.part) → commit(rename)
        │                                             └─ при 404/Unusable: recent_stamps() + попытки (до 5)
        │
        ├──► [AIMD-контроллер (тик 3 с)] ── читает win_bytes/win_files/win_429 → меняет gate.limit (1..24)
        │
        ├──► [recheck (1 поток)] ── раз в 120 с или 500 ok → CDX(from=watermark) → queue.push()
        │
        └──► [главный цикл (тик 500 мс)] ── ждёт done >= queue.planned(), каждые 500 файлов проверяет место
```

## 2. Детальный разбор работы алгоритма по каждому вопросу

### 2.1 Как алгоритм работает с потоками скачивания

1. **Подготовка очереди (`order_interleaved`, `src/core.rs:2795-2820`).** Список `todo` (исключая уже лежащие в `mirror/` непустые файлы) раскладывается по 4 корзинам (`html`, `code`, `img`, `other`), сортируется по `url` и перемешивается по кругу. Цель — все 4 полосы прогресса в UI двигаются одновременно, а мелкие/крупные типы перемешиваются.
2. **Пулинг и блокировка (`Queue::pop` + `Gate::acquire`, `src/core.rs:3086-3099`).** Все `self.workers` потоков стартуют сразу. Каждый поток:
   - берёт задачу из `Queue::pop()` (если очередь пуста, спит на `Condvar`, пока `recheck` не добавит задачу или главный поток не вызовет `queue.close()`);
   - затем запрашивает разрешение у `Gate::acquire()` — если число активных запросов `inflight >= gate.limit`, поток спит на `Condvar` шлюза `Gate`;
   - далее `fetch_one()` проверяет локальный диск, дедупликацию `dedup` (`hard_link`), делает запрос(ы) через `Shared::open()` (с учётом глобальной паузы `wait_if_paused()` и `--rate` в `rate_wait()`) и освобождает слот `gate.release()`.
3. **Узкое место захвата слота `Gate`.** Слот `Gate` удерживается на **всё** время `fetch_one()`, включая:
   - локальные операции проверки диска/дедупликации (быстро, но при `hard_link` синхронный I/O);
   - паузу `self.sleep(wait)` при `429` (`20 * (attempt + 1)` или `Retry-After` до `300 с`) и при сетевой ошибке (`0.6 * (attempt + 1)` с) внутри `attempt()`;
   - всю цепочку `recent_stamps()` + до `5` последовательных попыток старых снимков.
   Из-за этого при `429` или медленном `recent_stamps()` слот остаётся занятым и фактически исключается из активного скачивания других файлов, а повторная попытка удерживает его 20–40 секунд вхолостую.

### 2.2 Как алгоритм работает с количеством потоков (`--workers` против `Gate`)

В программе одновременно действуют **три разные переменные потоков**, что создаёт путаницу и в работе, и в отчётности:

1. `--workers N` (`src/main.rs:420`, `1..=64`, по умолчанию `16`) — задаёт **число ОС-потоков**, создаваемых в `download()`.
2. `Gate::limit` (`src/core.rs:26-27`, `363`, `391`) — динамический потолок одновременных выполнений `fetch_one()`, **жёстко ограниченный `[1, 24]`** и **всегда стартующий с `MIN_THREADS = 2`**.
3. `Progress::threads` (`src/core.rs:2960`) — в UI и CLI выводится `shared.gate.limit()`, а **не** `min(self.workers, gate.limit())`.

**Следствия из этого (подтверждены замерами на `samorez.pro`):**
- При `--workers 1` (`exp-w1`): реально скачивает **1 поток**, но AIMD-контроллер разгоняет `gate.limit` до `24`, и программа печатает в журнал `потоков=24`!
- При `--workers 2` (`exp-w2`): реально скачивают **2 потока**, но счётчик `потоков=` в логе доходит до `11`.
- При `--workers 48` (`exp-w48`): создаются **48 ОС-потоков**, но `Gate::set_limit` зажат константой `MAX_THREADS = 24` — больше 24 одновременных запросов никогда не запустится, а на `samorez.pro` реальный лимит AIMD вообще не поднялся выше `8`. Остальные 24–40 потоков простаивают на `Condvar` и держат стек/память без пользы.

### 2.3 Как алгоритм работает с управлением потоками (AIMD-контроллер)

Логика контроллера (`src/core.rs:2889-2923`, интервал опроса **3 с**):

```
if n429 > 0:
    bad_streak += 1
    if bad_streak >= 3:
        gate.limit = 2; pause(120s); bad_streak = 0
    else:
        gate.limit = max(1, limit / 2)
else if files > 0 && bps >= prev_speed * 0.95:
    gate.limit = min(24, limit + 1)
else if files > 0 && bps < prev_speed * 0.6:
    gate.limit = max(1, limit - 1)
```

В коде выявлены **четыре алгоритмических просчёта** этого контроллера:

1. **Ложное снижение потоков из-за неоднородности размеров файлов.** Если в прошлом 3-секундном окне завершился крупный CSS/JS/PNG (`prev_speed = 1055 КБ/с`), а в текущем завершились 5 мелких HTML/иконок по 1–2 КБ (`bps = 15 КБ/с`), условие `bps < prev_speed * 0.6` срабатывает как «канал просел» и **уменьшает `limit` на 1 без единого отказа сервера**. Это наблюдалось **во всех без исключения прогонах** (включая `exp-w1`..`exp-w48` и `exp-long400`), где `429` не было ни разу (`429=0`), а лимит постоянно прыгал вверх-вниз (`[2, 3, 2, 1, 2, 3, 4, 5, 6, 5, ...]`).
2. **Несброс `bad_streak` при чистом окне.** Переменная `bad_streak` сбрасывается в `0` **только** при достижении `3` (после паузы 120 с). Если окно с `429` произошло на 10-й секунде, второе на 200-й, третье на 500-й (между ними сотни чистых окон), третье единичное `429` всё равно запустит глобальную 2-минутную паузу и сброс до 2 потоков.
3. **Слепота к `503`, таймаутам и `10061`.** Веб-архив на перегрузке часто отвечает не `429`, а `503`, `10061 Connection Refused` (наблюдалось в `exp-resume`, `exp-long400-w16`) или таймаутом `per_read 30с` (в `exp-w24`). В `attempt()` все эти ошибки **не инкрементируют `win_429`**, а из-за `files == 0` при замирании `bps == 0` контроллер даже **не снижает** потоки, продолжая бить архив тем же числом соединений.
4. **Непотоковое начисление байтов (`win_bytes`).** В `save_body()` байты **не** передаются в `win_bytes` по ходу чтения чанков (`core.rs:1195-1197`) — они начисляются одномоментно в `fetch_one()` после переименования. На крупном файле в окне `3 с` регистрируется `bytes = 0, files = 0`, а в следующем окне — резкий всплеск `bps`, что ещё сильнее раскачивает AIMD. (Одновременно это расходится с ФТ-144 ТЗ «учитывать прочитанные байты по ходу чтения».)

### 2.4 Как алгоритм работает с обрывами потоков и докачиванием файлов

| Сценарий обрыва | Поведение в `3.6.5` (код + проверка) | Последствия |
|---|---|---|
| Ошибка соединения/TLS на `open()` | `attempt()` повторяет запрос **1 раз** (`0..2u32`, пауза `0,6 с`), затем `Attempt::Failed`, счётчик `errors += 1`. Не заносится в `no-snapshot.tsv` | Повторный запуск перекачает упавшие файлы. **Баг на русской Windows:** код `10061` не триггерит `https → http` в `scheme_switch_worthwhile()` |
| HTTP `429` в `attempt()` | Увеличивает `win_429`, ждёт `Retry-After` (до 300 с) или `20 с` (на 1-й попытке), делает 2-ю попытку; при второй `429` — `Attempt::Failed` (в `no-snapshot.tsv` не пишется) | Адрес не выпадает на неделю, будет повторён на следующем прогоне |
| HTTP `5xx` (напр. `503`) в `attempt()` | Повторяет 1 раз через `0,8 с`; после двух `5xx` → `Attempt::Failed` (учёт в `errors`, без `no-snapshot.tsv`). На AIMD не влияет | Быстрый повтор через 0,8 с часто снова попадает в окно перегрузки `503` |
| **Обрыв TCP/таймаут чтения посреди тела (`200 OK`, внутри `save_body()`)** | `save_body()` закрывает и **удаляет `.part`**, возвращает `Err(err)`. В `attempt()` ветка `Err(err) => Attempt::Failed` **делает немедленный `return` без второй попытки** (`src/core.rs:1164-1174`) | Потеря второй попытки; скачанный кусок полностью уничтожается (`Range` не поддерживается) |
| **Мягкая отмена пользователем (`cancel`)** | В `save_body()` проверяется перед каждым `reader.read` (шаг 64 КБ, но в пределах `timeout_per_read = 30 с`). `.part` удаляется сразу | Возвращает управление без мусорного файла в пределах одного чтения/блока |
| **Жёсткий обрыв процесса (`Kill`/сбой питания)** | Готовые файлы уже переименованы из `.part` (`move`) и **остаются целыми (0 нулевых файлов в `exp-resume-part1`: `49/49`)**. Недокачанные `.part` остаются на диске, а накопленные в памяти `content_types`, `no_snapshot`, `snapshots` и `dedup` **теряются** (пишутся только в конце `download()` / `build()`) | При повторном запуске: `49` готовых файлов пропускаются (`already on disk`), но: (а) они теряют `Content-Type` для кодировки и даты `snapshots.tsv`; (б) **баг в `cleanup_temp()` не удаляет оставшиеся `.part`-файлы** |
| **Докачивание после обрыва (повторный запуск)** | На уровне файла докачки по HTTP `Range` **нет** (файл скачивается с 0 байта). На уровне очереди: файлы в `mirror/` с `len > 0` пропускаются, адреса из `no-snapshot.tsv` пропускаются 7 дней, адреса с прошлым `errors` качаются заново | **Скрытая проблема:** при новом запуске заново выполняется весь `inventory` CDX (60–250 с); если очередная страница CDX упадёт с `503/10061`, `limit_order` соберёт **другой** срез при `--limit > 0` (подтверждено в `exp-resume-pass3`) |

## 3. Результаты реальных раздельных исследований на `samorez.pro`

Все запуски выполнены одним и тем же релизным бинарником `3.6.5` (`SiteRestorer-windows-x64-cli.exe`, `SHA-256: 56cc08ee...`), в **отдельные чистые каталоги** (кроме сценария докачки `exp-resume`), с **обязательными перерывами 35–60 с** между прогонами, чтобы не накладывать лимиты архива друг на друга. Инструмент сбора и анализа: `scratch\sr-bench\run_exp.ps1`, `scratch\sr-bench\probe_keepalive.py`, `scratch\sr-bench\analyze_logs.py`.

### 3.1 Контрольный зонд: keep-alive против нового TCP+TLS соединения на `web.archive.org`

Выполнено 10 последовательных `GET /web/<ts>id_/<url>` по реальным URL `samorez.pro` из `inventory.jsonl`: сначала на одном переиспользуемом соединении (`Connection: keep-alive`), через 5 с — на новых соединениях (`Connection: close`, имитация вытеснения из пула `ureq` при `>3` потоков).

| Режим | Запрос 0 (холодный TCP+TLS) | Среднее по запросам 1..9 (или 0..9) | Медиана | Итог |
|---|---|---|---|---|
| Постоянное соединение (`keep-alive`) | `1 584,0 мс` | **`788,8 мс`** (запросы 1..9) | `711,6 мс` | Все 10 ответов `200`, переиспользование экономит handshake |
| Новое соединение на каждый запрос | `1 915,2 мс` | **`1 615,7 мс`** (запросы 0..9) | `1 341,1 мс` | **В 2,05× медленнее** (`+826,9 мс` лишней задержки на каждом запросе) |

### 3.2 Серия A: зависимость скорости от числа потоков (`--limit 150 --fallback-depth 0 --rescue-limit 0`)

## 4. Оценка оптимальности и способы достижения большей скорости

### 4.1 Оптимален ли текущий алгоритм для максимальной скорости?

**Нет.** В текущей реализации `3.6.5`:
- Потолок реальной пропускной способности на `samorez.pro` в `download()` — `3,1–3,8 файлов/с` (`150–200 КБ/с`), тогда как задержка одного тёплого keep-alive запроса к `web.archive.org` равна `~790 мс` (`~1,27 req/s` на 1 соединение). При 8 полноценных постоянных соединениях теоретический потолок без `429` составляет **`8 × 1,27 ≈ 10,1 req/s`** (более чем в **2,5–3 раза быстрее** текущих `2,92–3,78 ф/с`), а для мелких ресурсов узким местом становится не канал (`9,4 МБ` за `50 с` = `1,5 Мбит/с`), а **лишние TCP+TLS handshake, старт с `2` потоков и ложные откаты AIMD**.
- С учётом этапа `inventory` (который в `7` из `11` прогонов был дольше самого `download`: `92–250 с`) суммарная скорость восстановления сайта ограничивается ещё сильнее.

## 5. Что не проверено и почему

1. **Поведение AIMD-контроллера при реальной массовой серии `429 Too Many Requests` (срабатывание 120-секундной паузы после 3 окон подряд):** за всю серию экспериментов на `samorez.pro` (14 запусков) `web.archive.org` не вернул ни одного `429` (`429=0`), ограничиваясь `503` на CDX и `10061`/таймаутами на файлах. Реакция на `429` проверена по коду (`core.rs:2904-2916`) и модульным тестам `core.rs`, но не воспроизведена на живом архиве.
2. **Обрыв посреди крупного файла (>10–50 МБ) для замера длительности существования `.part` и скорости отмены по блокам 64 КБ:** на первых `400` файлах `samorez.pro` средний размер файла составил ~39 КБ (в `exp-w1..w48` ~64 КБ), поэтому запись каждого файла завершалась за миллисекунды. Отказ внутри `save_body()` и отсутствие повторной попытки при нём установлены чтением кода (`src/core.rs:1164-1174`, `1198-1244`).
3. **Пайплайн полной копии `samorez.pro` целиком (`8 928` адресов без `--limit`):** для раздельного замера нескольких режимов без блокировки IP архивом использовались срезы `--limit 150`, `300`, `400`.
4. **Правка кода:** в данной задаче выполнялось только исследование и измерение релизной версии `3.6.5`; код в `D:\dev\sr-docs\src\` не изменялся.

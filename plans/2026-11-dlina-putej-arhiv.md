# Длина пути к файлу в веб-архиве: что происходит за пределом ОС и как это решить

| Поле | Значение |
|---|---|
| Статус | разбор, решение предложено (код не менялся) |
| Дата | 14.11.2026 |
| Версия изделия | 3.6.2 |
| Основание | вопрос владельца: «что будет если длина пути к файлу в веб архиве превысит допустимую в системе (windows или linux), как обойти / решить эту проблему» |
| Требования, в которые упирается | ФТ-45 (не прерывать прогон из-за длинного пути, иначе понятная причина), ФТ-75 (детерминированный путь), БЗ-6 (сегмент ≤ 80 символов, путь ≤ 160), НД-6 (длинные пути не ломают прогон) |

## 1. Короткий ответ

До пределов операционной системы путь из архива **не доходит**: программа сама укорачивает имена
детерминированно — сегмент до 80 символов, весь относительный путь до 160 символов, а всё, что
длиннее, сводится в `<первый сегмент>/_long/<хеш>.ext`. Проверено зондом: адрес из 60 вложенных
каталогов даёт путь `segment00/_long/f5d253df.html` (29 символов), адрес с 200 эмодзи — 80 символов.

Предел ОС может быть достигнут по другой причине — из-за **глубокого каталога вывода** (`--out`).
Что тогда:

| Платформа | Предел | Что делает программа | Итог |
|---|---|---|---|
| Windows 10/11 | 260 символов без опции длинных путей, до 32 767 с ней | в манифесте `longPathAware=true` (проверено в собранном exe), удаления и обход идут через `\\?\` | работает |
| Windows без опции (политика выключена, старые сборки) | 260 | запись падает с ошибкой ОС 206, попадает в журнал как «не удалось записать …»; обход дерева **молча пропускает** глубокие каталоги | часть файлов не собрана, числа отчёта занижены |
| Linux | `PATH_MAX` 4096 байт, `NAME_MAX` 255 байт на имя | предел сегмента считается **в символах** (80), а не в байтах | имена из 64–80 четырёхбайтных символов дают `ENAMETOOLONG` |

То есть сегодняшнее поведение: **архивный путь никогда не выходит за предел**, а оставшиеся три
дыры (обход без префикса, счёт в символах на Linux, отсутствие понятного сообщения) — предмет
доработки; конкретные правки в §5.

## 2. Что делает код сейчас

| Механизм | Где | Что именно |
|---|---|---|
| Предел сегмента | `src/paths.rs:7`, `safe_seg` (`src/paths.rs:65–92`) | сегмент длиннее 80 символов → первые 60 символов + `_` + FNV-1a 32 (`8 знаков`); запрещённые символы заменяются, зарезервированные имена (`con`, `nul`…) получают `_` в начале |
| Предел пути | `src/paths.rs:6`, `src/paths.rs:138–150` | относительный путь длиннее 160 символов → `<первый сегмент>/_long/<fnv(url)><расширение до 6 знаков>` |
| Поддомены | `src/paths.rs:105–118` | к пути добавляется сегмент хоста — он проходит тот же `safe_seg`, поэтому тоже ≤ 80 |

Требования, которые это реализуют: БЗ-6 (80/160), ФТ-45 (сокращать детерминированно, иначе понятная
причина), ФТ-75 (один адрес — один путь), НД-6 (длинные пути не ломают прогон).

## 3. Проверки работой

### 3.1. Зонд фактических путей (временный тест в `paths.rs`, затем удалён)

| Вход | Результат |
|---|---|
| сегмент из 70 эмодзи (4 байта каждый) | 70 симв. / **280 байт**, обрезки нет — предел считается в символах |
| сегмент из 200 эмодзи | обрезан: 60 эмодзи + `_3e701805` = **249 байт**, путь 80 символов |
| 60 вложенных каталогов `segmentNN` | `segment00/_long/f5d253df.html` — 29 символов |
| 120 символов «я» (2 байта) | 69 симв. / 129 байт в сегменте |

Вывод: свёртка работает и держит пути короткими; но окно 64–80 четырёхбайтных символов проходит
без обрезки.

### 3.2. Linux: предел имени в байтах (WSL, Kali, ext4, `/tmp`)

`os.pathconf`: `NAME_MAX = 255`, `PATH_MAX = 4096`. Создание файла:

| Имя | Байт | Итог |
|---|---|---|
| 60 эмодзи | 240 | создан |
| 63 эмодзи | 252 | создан |
| **64 эмодзи** | **256** | **errno 36, File name too long** |
| 100 символов «я» | 200 | создан |

То есть сегмент из 64–80 четырёхбайтных символов на Linux не создаётся — ровно тот случай, который
сегодняшний предел (80 **символов**) пропускает.

### 3.3. Windows: длинная запись на этой машине

Каталог 327 символов, файл 338 символов (`…\уровень-12-длинное-имя\site\index.html`):

| Способ | Результат |
|---|---|
| `Set-Content` из pwsh 7 (манифест `longPathAware`) | файл 17 Б создан |
| `cmd /c echo` (без манифеста) | файл 6 Б создан — потому что на машине включена политика |
| запись через `\\?\` префикс | файл 2 Б создан |

Политика: `HKLM\SYSTEM\CurrentControlSet\Control\FileSystem\LongPathsEnabled = 1`. Поэтому отказ
на этой машине воспроизвести нельзя — нужны система с выключенной политикой или Windows без
поддержки `longPathAware`.

## 4. Что происходит при превышении — по шагам

1. **Инвентаризация.** Путь ещё не используется, только адрес: длина на этом шаге не влияет.
2. **Загрузка.** `create_dir_all` + `File::create` обычным путём. Если предел достигнут: ошибка
   попадает в журнал строкой «запись: …» (`src/core.rs:1038–1044`) или «не удалось записать …»
   (`log_write_error`), адрес считается сбойным. Тихой потери нет — это закрыто в 3.4.0 (ОШ-8).
3. **Сборка.** Переименование `.part` → файл: при отказе пробуется `remove_file` + `rename`, затем
   `copy` (1129–1141). Копирование в копию: ошибка логируется с относительным путём (3017–3030).
4. **Обход дерева.** `walk_files` читает каталог **без префикса** и молча пропускает тот, который
   прочитать не удалось. Последствия: неверное число файлов в отчёте, не удаляются «сироты», часть
   страниц не попадает в проверку ссылок. На системе с включённой поддержкой длинных путей
   не проявляется.
5. **Очистка прошлой копии.** Работает через `remove_tree` + `\\?\` — это и был ОШ-7, закрыт в 3.4.0.

## 5. Как решить: четыре правки по приоритету

### 5.1. Считать предел сегмента в байтах (Linux, ~10 строк)

Причина: `NAME_MAX` измеряется в байтах, наш предел — в символах. Правка в `safe_seg`:

```rust
// было: if seg.chars().count() > MAX_SEG_LEN
if seg.chars().count() > MAX_SEG_LEN || seg.len() > MAX_SEG_BYTES {
    let cut: String = seg.chars().take(60).collect();
    seg = format!("{cut}_{}", fnv_hex(&seg));
}
```

где `MAX_SEG_BYTES = 200` (60 четырёхбайтных символов = 240 байт + 9 на хеш = 249 < 255 — с запасом).
Плюс тест: сегмент из 70 эмодзи должен получить `len() <= 255`.

### 5.2. Все файловые операции — через `long_path` (Windows без политики, сетевые шары, ~15 строк)

Причина: сегодня запись полагается на манифест; удаление — на префикс. Разнобой и есть источник
отказов там, где манифест не действует (Windows 7/8.1, старые SMB-серверы, чужие файловые системы).
Правка: обернуть `create_dir_all`, `File::create`, `rename`, `copy`, `read_dir` в `long_path(…)`.
Условия уже выполнены: путь вывода абсолютный (`Engine::new`), а нормализация `..` не нужна — сегменты
строятся из `safe_seg`, где `..` нейтрализован.

### 5.3. Проверка длины до прогона и понятное сообщение (ФТ-45)

Сейчас при ошибке пользователь видит системный текст («The filename or extension is too long.
(os error 206)») без подсказки. Правка: перед прогоном считать длину `out/mirror` и, если она больше
безопасного порога (240 символов без поддержки длинных путей, 4000 байт на Linux), сообщать:
«каталог вывода слишком глубокий: сократите --out» — и/или сразу уходить в `_long/` на один уровень
раньше. Ошибку записи распознавать по коду (`ERROR_FILENAME_EXCED_RANGE` = 206, `ENAMETOOLONG` = 36)
и писать по-русски с советом.

### 5.4. Обход дерева: не глотать ошибку чтения каталога (отчёт не должен врать)

`walk_files` сейчас делает `else { continue }`. Правка: считать непрочитанные каталоги и выводить их
число в отчёт строкой «каталогов не прочитано: N» — тогда расхождение чисел перестаёт быть молчаливым
(это тот же класс, что ОШ-7 и Д-101).

## 6. Как проверить после правки

1. `cargo nextest run --release` — новые тесты: сегмент из 70 эмодзи (байты), путь из 60 каталогов
   (свёртка), обход дерева с каталогом, который не читается (счётчик в отчёте).
2. WSL: создать копию с именем из 70 эмодзи — прогон должен завершиться, файл лежать под свёрнутым
   именем; повторный прогон — без изменений (детерминизм).
3. Windows: `--out` глубиной 300+ символов на системе с `LongPathsEnabled=0` — файлы пишутся,
   в отчёте нет расхождения, при отказе видно понятное сообщение.
4. Проверить, что `_long` не сталкивается: два разных адреса дают разные хеши (FNV-1a 32; при
   желании — проверка на 100 тыс. адресов).

## 7. Что проверено и что нет

**Проверено:** свёртка сегмента и пути (зонд, `paths.rs`), предел `NAME_MAX`/`PATH_MAX` и отказ на
64 эмодзи (WSL, ext4), запись файла на пути 338 символов тремя способами (Windows), наличие
`longPathAware` в собранном exe (`mt.exe`), политика `LongPathsEnabled=1` на машине, места кода
(`paths.rs`, `core.rs`, `build.rs`, манифест), тексты требований ФТ-45/ФТ-75/БЗ-6/НД-6 и запись ОШ-7
в реестре дефектов.

**Не проверено:**

1. Отказ записи на Windows при выключенной политике — на этой машине политика включена, а менять
   системные настройки без разрешения владельца нельзя.
2. Живой прогон с глубоким `--out`: в момент проверки архив отвечал медленно (CDX в программе
   уходил в таймаут при 5 попытках, `curl` при этом получал 200 за 0,6–0,9 с), поэтому копия не
   собралась и запись файлов движком не наблюдалась. Тесты на длину пути от сети не зависят.
3. Копирование в `site` и переименование `.part` на путях > 260 — проверяется только на системе
   без поддержки длинных путей.

## 2. Найденные дефекты

### Р-1 (высокий). Паника в рабочем потоке убивает всё приложение без сообщения

**Проявление.** В релизной сборке `panic = "abort"` (`Cargo.toml:48`). Движок работает в отдельном потоке (`src/app.rs:323`), загрузка — ещё в четырёх (`core.rs:2555`, `2596`, `2650`, `2747`), и ни в одном месте нет `catch_unwind`, нет `std::panic::set_hook`, нет записи аварийного лога (проверено `rg`: 0 вхождений). Любая паника в любом потоке — мгновенное завершение процесса: окно исчезает, консоль не печатает ничего, пользователь не знает причины.

**Почему это не то же, что Д-88.** В реестре записано «паника рабочего потока в окне не видна: прогон просто останавливается». При `panic = "abort"` останавливается не прогон, а процесс — и никакой «прогон продолжится» не произойдёт.

**Оценка риска.** 59 `unwrap/expect` в рабочем коде `core.rs` — почти все на мьютексах и статических регексах, то есть безопасны при `abort` (отравления нет). Реальный риск дают срезы строк по байтовым индексам и арифметика в разборе CDX/журнала: один необычный ответ архива — и процесс умирает. Доказать конкретную панику живьём не удалось (нет доступа к архиву), поэтому это оценка по коду, а не воспроизведённый случай.

**Что делать.** Один из двух путей: (а) `panic = "unwind"` в профиле релиза для GUI-сборки и `catch_unwind` вокруг `engine.run()` с показом ошибки в окне; (б) оставить `abort`, но поставить `set_hook`, который пишет `data/crash.log` (поток, сообщение, `RUST_BACKTRACE`) и, для GUI, показывает окно сообщения до `abort`. Вариант (б) дешевле и не меняет поведение по памяти.

**Как проверить.** Тест с намеренной паникой в рабочем потоке: процесс должен оставить `crash.log` с причиной (или показать сообщение), а не исчезнуть.

### Р-2 (высокий). Числовые аргументы CLI разбираются молча: опечатка превращает пробу в полный прогон

**Проявление.** В `parse_args` (`src/main.rs:343`, `349-350`, `354`, `377`, `381`, `393`, `397`, `401`, `409`, `417`) любой числовой флаг читается как `args.get(i + 1).and_then(|v| v.parse().ok()).unwrap_or(<значение по умолчанию>)`. Следствия:

- `--limit abc` → `limit = 0`, а `0` означает «без ограничения»: вместо пробы на 10 адресов идёт полный обход сайта (у меня на 20 адресах прогон занял 297 с; на сайте с 50 000 адресов это часы и десятки тысяч запросов к архиву);
- `--limit -5` → то же самое: `usize` не разбирает минус, значение молча становится «без лимита»;
- `--workers abc` → 16, `--refresh-days вчера` → 30, `--stub-bytes x` → 256 — без единого слова;
- `--site --out D:\x` → в `site` попадает `--out`, а `D:\x` съедается как «следующий аргумент»; пользователь получает «плохой адрес» вместо «забыли значение для --site».

**Почему это отдельный дефект от Д-85.** Д-85 закрыл только *имена* флагов (неизвестный флаг теперь печатает предупреждение). Значения не проверяются вообще, а именно они задают объём работы.

**Что делать.** Разбор значением: `--limit` → `parse::<usize>()` с ошибкой и кодом 2 при неудаче; пустое значение после флага — ошибка «у --limit нет значения»; проверка диапазонов (`--limit 0` разрешён явно, `--workers 1..=64`, `--refresh-days 0..=3650`). Тесты: по одному на каждый флаг с мусорным значением, ожидание — код 2 и понятный текст.

**Как проверить.** `site-restorer --cli --site example.com --limit abc` → код 2, текст «--limit: ожидается число», ни одного запроса к архиву.

### Р-3 (средний). Схема доступа к архиву переключается молча и обратимо: часть прогона идёт по незашифрованному http

**Проявление.** `switch_archive` (`core.rs:529-541`) меняет схему через `fetch_xor(true)` — то есть **переключает**, а не «уходит на запасную навсегда». Вызывается на любую сетевую ошибку: `attempt()` (`core.rs:973`), отказ списка адресов (`2054`), отказ страницы индекса (`2270`). Сообщение в журнал пишется один раз за прогон (`archive_switch_logged.swap(true)`), дальше все переключения беззвучны. В `RESULT` и в `report.html` схемы нет. Требование ТЗ прямо противоположно: ФТ-116 и §4.3 «Схема доступа» — «рабочая схема запоминается до конца прогона», то есть переключение должно быть однократным и липким. Значит это не только вопрос вкуса: код расходится с требованием.

**Живое подтверждение.** Прогон `--limit 3`: `сеть: timeout: connect` (https) → `архив: сеть недоступна, переключаюсь на http://web.archive.org` → весь дальнейший прогон по http. Следующий прогон: `ошибка io … (os error 10061)` → снова переключение. При нестабильной сети (а с этой машины `web.archive.org` сейчас недоступен даже `curl`) прогон может ходить по обоим схемам вперемешку, и пользователь об этом узнает только по одной строке в начале.

**Влияние.** Данные из архива по http не аутентифицированы: содержимое копии может быть подменено в канале, а копия позиционируется как «восстановление своего сайта». Пользователь не может ни узнать схему, ни запретить переход.

**Что делать.** (1) Переключаться только после N подряд неудач на https (сейчас — после первой); (2) вернуться на https при первом успехе, а не по следующей ошибке; (3) писать в журнал каждое переключение и в `RESULT`/отчёт — итоговую схему (или счётчики запросов по каждой); (4) флаг `--no-http-fallback` для тех, кому важна целостность.

### Р-4 (средний). Отчёт занижает число ссылок: «Внутренних ссылок 6» при 77 атрибутах в копии

**Проявление.** В собранной копии (17 HTML-страниц) 72 вхождения `href` и 5 — `src`. Отчёт печатает «Внутренних ссылок: 6», «Битых ссылок (нет в копии): 1». Причина: считается не то, что есть в копии, а то, что прошло через `ref_key` (`core.rs:3246`), который отбрасывает значения с `#`, пробелами, скобками, кавычками, запятыми и `*`. Остальные ссылки не проверяются и в счётчик не попадают; отдельного счётчика «не проверялось» нет.

**Почему это важно.** Число «битых 1» читается как «копия целая». Фактически проверено 8 % ссылок. В копии при этом осталось 13 абсолютных ссылок на тот же сайт (`http://info.cern.ch/hypertext/WWW/TheProject.html`) — офлайн они не работают, и в отчёте они видны только косвенно, строкой «Адресов оставлено (нет в копии): 15».

**Что делать.** Разделить в отчёте три числа: «проверено», «не проверено (не подлежит проверке)», «битых». В `verify` уже есть и `known`, и `ref_targets` — нужен только счётчик отброшенных `ref_key` значений и подпись в шаблоне (`REPORT_TMPL`, `core.rs:5066+`).

### Р-5 (низкий). Потолка размера тела нет, контроль места — только предварительный

**Проявление.** `read_all` (`core.rs:610`) и `read_progress` (`630`) читают тело в `Vec` без предела: ответ индекса в сотни мегабайт (или подменённый ответ) даёт рост памяти, а не ошибку. Контроль свободного места есть, но однократный: `check_space()` (`core.rs:4022`) вызывается один раз перед загрузкой (`core.rs:3915`) и считает потребность как сумму длин записей индекса ×3 (`estimate_bytes`, `1857`). Две дыры: (1) если индекс не отдал длины (`need == 0`), проверка молча пропускается (`core.rs:4027`); (2) во время загрузки место не перепроверяется — на многочасовом прогоне заполнение диска сторонним процессом даёт серию «ошибок загрузки» вместо «место кончилось».

**Влияние.** Умеренное: предварительная оценка ловит основной случай (мало места до старта), но не деградацию в процессе и не экзотические ответы.

**Что делать.** (1) При `need == 0` писать в журнал «оценка места недоступна — проверка пропущена» (сейчас молчание); (2) перепроверять место раз в N файлов (например, каждые 500) и останавливать прогон с тем же текстом, что в `check_space`; (3) предел на тело ответа индекса (например, 512 МБ с ошибкой «ответ индекса слишком велик»).

### Р-6 (средний). `User-Agent` заявляет версию 2.0

**Проявление.** `core.rs:18-19`: `"SiteRestorer/2.0 (offline mirror tool; respectful crawler; contact: local user)"` при версии 3.6.1. `--version` печатает 3.6.1, а архив видит 2.0.

**Влияние.** Разбор жалоб «архив ограничивает» и любые правила для клиентов по UA опираются на неверную цифру; в 3.6.0/3.6.1 менялось поведение (32-битные сборки, AIMD, потоковая запись), а UA об этом не говорит.

**Что делать.** Собирать UA из `env!("CARGO_PKG_VERSION")` (константа времени компиляции, без затрат) и добавить в тест сверку с `APP_VERSION`.

### Р-7 (средний). `Retry-After` понимается только как число секунд

**Проявление.** `core.rs:584-600`: значение парсится как `f64`; форма HTTP-даты (`Retry-After: Wed, 21 Oct 2026 07:28:00 GMT`), которую стандарт допускает и которую отдают прокси и CDN, не разбирается — пауза берётся по умолчанию (20 с × попытка). При строгом лимите это лишние 429 и потерянные адреса (в `attempt` всего 2 попытки, `core.rs:956`).

**Что делать.** Разбирать обе формы: число и `stamp_from_http_date` (функция уже есть, `core.rs:4335`). Тест на дату в `Retry-After`.

### Р-8 (низкий). TLS-доверие — встроенные корни, а не системное хранилище

**Проявление.** В сборке виден `webpki-roots 1.0.11` (лог `cargo build`), `ureq` подключён с умолчаниями (`Cargo.toml:35`). Это значит: доверяются только корни, вкомпилированные в крейт. В сети с MITM-прокси, антивирусной подменой TLS или с корпоративным/национальным УЦ соединение не установится, а сообщение будет «сеть недоступна» — то есть пользователь увидит Р-3 (переключение на http) вместо «сертификат не принят».

**Что делать.** Либо фича `native-roots` (если доступна в выбранной версии `ureq`), либо явное сообщение при ошибке сертификата: «сертификат архива не проходит проверку — вероятен прокси/антивирус», без переключения на http. Проверить на машине с подменой сертификата.

### Р-9 (низкий, долг). Мелкие расхождения и мёртвые места

- `--verbose` понимается в `main()` (для `--version`), но не в белом списке `parse_args` (`src/main.rs:414`): `--cli … --verbose` печатает «неизвестный аргумент». Наблюдал в своём прогоне.
- Комментарий в `commit` (`core.rs:1093-1096`) утверждает, что «Windows: rename НЕ перезаписывает существующий файл». По документации `std::fs::rename` на Windows используется `MoveFileEx` с `MOVEFILE_REPLACE_EXISTING`, то есть перезаписывает; реальная причина отказов — занятый файл (sharing violation). Логика с `remove_file` + `copy` остаётся полезной, но обоснование неверно и вводит в заблуждение при следующей правке.
- `remove_tree` (`core.rs:4931`) и `walk_files` (`5040`) не отличают каталог-ссылку (junction) от обычного каталога: при удалении можно выйти за пределы копии, если внутри `site\` окажется junction. Вероятность низкая (каталоги создаёт сама программа), но проверка `file_type().is_symlink()` стоит одну строку.
- `--limit N` берёт первые N адресов по порядку `urlkey` — на старых доменах это мусорные адреса (`/%22`, `/%22Cern`, `/%22target=%22_blank` в моём прогоне), а не главная страница. Для «быстрой пробы» полезнее начинать с `/`, затем с самых «тяжёлых» разделов.

Сверка с диском: HTML-страниц в копии 17 — совпало с `pages`; файлов 22 — совпало с `files` и `mirror`. То есть ПРМ-8 по этим полям выполняется.

Тесты на это есть и они не формальные.

- **Контроль места до старта.** `check_space()` (`core.rs:4022`) сравнивает сумму длин записей индекса ×3 с остатком на диске и останавливает прогон с понятным текстом «недостаточно места: нужно около N МБ» — Д-15 выполнено, проверено чтением.
- **Коды возврата CLI.** 0 — успех, 1 — ошибка, 2 — неверное использование, 130 — остановка пользователем (совместимо с `SIGINT`).
- **Отчёт.** `report.html` создаётся всегда, числа по типам, годам снимков, доборам и перезаписям осмысленны; шаблон без внешних зависимостей.

Долг проявляется конкретно: найденные Р-3 (схема архива) и Р-4 (числа отчёта) — обе правки упираются в то, что политика (что считать ссылкой, что считать успехом) перемешана с механизмом (сокеты, файлы, шаблон отчёта). Пока `verify` и шаблон отчёта живут внутри движка, «показать три числа вместо одного» требует правки ядра.

Предложение по разбиению (без переписывания, по швам, которые уже видны в коде):

1. `archive.rs` — адреса архива, схема (Р-3), `Retry-After` (Р-7), `open/fetch`; трейт `Archive` с одной реализацией `Wayback` и тестовой `Stub`. Даёт тесты без сети.
2. `download.rs` — `attempt`, `save_body`, `commit`, `link_shared`, `Gate`, `Queue`.
3. `build.rs` (модуль, не сборочный скрипт) — `rewrite_ref`, `ref_key`, `Index`, `rel_from`, кодировки.
4. `verify.rs` + `report.rs` — `verify`, `REPORT_TMPL`, `Outcome`.
5. `core.rs` остаётся «дирижёром»: `Engine::run` и этапы.

Порядок безопасный: сначала вынести `report` (чистая функция от `Outcome`), затем `verify`, затем `archive` с трейтом. Каждый шаг — отдельный коммит, гейты те же.

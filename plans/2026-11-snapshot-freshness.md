# Свежесть снимков: как устроен веб-архив и что мы из него берём

**Статус:** анализ закончен, план работ ниже. Дата: 11.11.2026.
**Задача:** в копию попадают страницы 2015 года при наличии снимков 2025–2026. Нужно понять,
какие данные об индексе у нас есть, можно ли определить самую свежую версию страницы и как её
скачивать.

---

## 1. Короткий ответ

**Можно.** Архив отдаёт снимок, ближайший к запрошенной дате, и сообщает фактическую дату снимка
заголовком `Memento-Datetime`. Наш код просит самый **старый** снимок каждого адреса, потому что
берёт отпечаток времени из списка адресов, а этот список уже схлопнут архивом до первой копии.

Проверено живьём на `011.vuejs.org` (сайт жил до 2023, но снимки есть и 2025–2026):

| Что просим | Что получаем |
|---|---|
| наш текущий запрос: `/web/20151101133431id_/` | снимок **2015-11-01** |
| `/web/2026id_/` (цель — сегодня) | снимок **2025-11-15** (последний в архиве) |
| CDX `limit=-1` для этого адреса | `20251115050209` — тот же, 2025-11-15 |

На `nginx.org` запрос «цель — сейчас» вернул снимок **10.11.2026** (вчера), при этом наш список
адресов для этого домена состоит из снимков 2008–2015 годов.

**Вывод:** свежесть определяется не архивом, а тем, какое время мы подставляем в адрес
воспроизведения. Один параметр в запросе — и копия становится современной.

---

## 2. Как устроен веб-архив

**Хранение.** Архив хранит не «страницы сайта», а **записи WARC** — сырые HTTP-обмены, сгруппированные
в файлы по обходам (имя файла видно в ответе: `x-archive-src: spn2-20261110161729-wwwb-spn18…warc.gz`).
Один снимок = один HTTP-ответ, записанный в WARC со своим временем. Одинаковое содержимое не
дублируется: повторная запись хранится как «revisit» со ссылкой на первый по `digest`.

**Индекс.** Поверх WARC лежит CDX-индекс — плоская таблица записей, отсортированная по `urlkey`
и времени. Строка CDX (пример из документации):

```
org,archive)/ 19970126045828 http://www.archive.org:80/ text/html 200 Q4YULN754FHV2U6Q5JUT6Q2P57… 1415
urlkey       timestamp       original                  mimetype  status digest                     length
```

- `urlkey` — канонический ключ адреса (`орг,домен)/путь`): в нём нет схемы, `www.`, порта и регистра.
  Именно по нему работает `collapse=urlkey`.
- `timestamp` — время снимка (14 цифр); `original` — исходный адрес как был запрошен;
  `statuscode` — код ответа; `digest` — SHA-1 содержимого (основа дедупликации);
  при запросе `fl=…offset,filename` отдаются файл WARC и смещение записи в нём.

**Воспроизведение.** Адрес `/web/<ts>/<адрес>` отдаёт снимок, **ближайший** к `<ts>` (не обязательно
точный). Суффикс `id_` — «как есть», без переписывания ссылок архивом: `/web/<ts>id_/<адрес>`.
Ответ содержит:

| Заголовок | Значение |
|---|---|
| `Memento-Datetime` | **фактическое время отданного снимка** (то, чего нам не хватает) |
| `X-Archive-Src` | файл WARC, откуда взята запись |
| `X-Archive-Orig-*` | заголовки исходного сервера: тип, длина, `Last-Modified`, `Date` |
| `Link: rel="original"`, `rel="timemap"` | исходный адрес и ссылка на список всех снимков |

Если снимка нет вовсе — ответ **404** без `Memento-Datetime` (страница-заглушка архива).

**Ограничения доступа.** Архив отвечает `429`/`503`/`504` на частые и на большие выборки; в дни
испытаний (11.11.2026) это наблюдалось регулярно: три запроса из десяти уходили в повтор.
Отсюда — обязательные паузы и повторы, которые в продукте уже есть.

Источник: [документация CDX-сервера](https://github.com/internetarchive/wayback/blob/master/wayback-cdx-server/README.md).

## 3. Что программа запрашивает сейчас

| Шаг | Запрос | Что получаем |
|---|---|---|
| 1 | `?showNumPages=true` | число страниц индекса — только для прогресса |
| 2 | `?fl=timestamp,original,mimetype,statuscode&filter=statuscode:200&collapse=urlkey&limit=50000` | до 50 000 строк: **по одной на адрес**, самая ранняя копия |
| 3 | `/web/<ts>id_/<адрес>` на каждый файл | снимок, ближайший к `<ts>` |
| 4 | если нет — `/web/<текущий год>id_/`, −1, −2 года | запасные попытки |

Код: `src/core.rs:849-890` (запросы индекса), `1097-1112` (отбор по адресу), `1114-1128` (сортировка,
`--limit`), `415-427` (адреса воспроизведения и запасные годы).

**Что мы выбрасываем из индекса:** `statuscode` (кроме фильтра), `digest`, `length`, `offset`,
`filename`. Из полученного ответа не читаем ни `Memento-Datetime`, ни `X-Archive-Src`, ни
`X-Archive-Orig-*` — то есть фактическую дату скачанного файла мы не знаем и нигде не показываем.

**Где теряется свежесть.** `collapse=urlkey` схлопывает записи «все, кроме первой» — документация
говорит прямо: «all captures after the first one that are duplicate are filtered out». Порядок
сортировки индекса — по `urlkey`, затем по времени, то есть первая запись = **самый ранний** снимок.

## 4. Что умеет индекс сверх того, что мы используем

| Возможность | Параметр | Проверено |
|---|---|---|
| Последние снимки адреса | `limit=-N` (N последних), `fastLatest=true` | да: `limit=-1` → `20251115050209` |
| Окно по времени | `from=`, `to=` (1–14 цифр) | да: `from=2024` отбросил снимки 2015–2023 |
| Схлопывание по содержимому | `collapse=digest` | не проверяли |
| Пагинация | `page=N`, `showNumPages=true` | уже используем |
| Продолжение с ключом | `showResumeKey=true`, `resumeKey=` | не проверяли |
| Все снимки адреса | `/web/timemap/json?url=…&limit=-2` | да, отдаёт последние два |
| Фильтры по полям | `filter=statuscode:200`, `filter=!mimetype:text` | да |

**Важная особенность.** `limit=-N` возвращает последние N строк в порядке сортировки **всего
результата**. Для точечного адреса это «самые свежие снимки», а для домена — просто последние по
алфавиту адреса. Проверено: `url=011.vuejs.org&matchType=domain&limit=-2` вернул два снимка
`js/vue.min.js` (2026), а не самые свежие страницы. Поэтому «свежее по домену» одним параметром
не получить — нужен либо обход с окном, либо воспроизведение с целевой датой.

## 5. Измерения

| Проверка | Результат |
|---|---|
| `011.vuejs.org/`, цель 2026 | снимок 2025-11-15, `Memento-Datetime` есть |
| `011.vuejs.org/`, наш отпечаток 2015 | снимок 2015-11-01, 6 751 байт (разница 10 лет) |
| `011.vuejs.org/js/vue.min.js`, цель 2026 | снимок 2026-10-22 (ресурсы тоже освежаются) |
| `nginx.org/`, цель 2026 | снимок 10.11.2026 (вчера), `X-Archive-Src` = spn2-20261110… |
| `nginx.org` без снимка (`/no-such-page-xyz/`) | 404, `Memento-Datetime` отсутствует |
| Список `nginx.org` без окна | 50 000 адресов (упёрлись в предел), годы 2008–2015 в начале |
| `011.vuejs.org` без окна | 53 адреса, годы 2015–2024, 48 с |
| `011.vuejs.org` `from=2024` | 45 адресов, только 2024–2026, 87 с (с двумя повторами из-за 504) |
| `011.vuejs.org` `from=2025` | 40 адресов, только 2025–2026 |

Отсюда: **окно по времени одновременно и освежает выборку, и сокращает список** (мёртвые адреса
выпадают), но стоит времени и делает запрос чувствительным к отказам архива.

## 6. Три способа получить свежий снимок

| Способ | Цена | Что даёт | Ограничение |
|---|---|---|---|
| **A. Целевая дата при воспроизведении**: `/web/<цель>id_/адрес` | 0 лишних запросов | самый свежий снимок, ближайший к целевой дате | дату фактического снимка надо читать из ответа |
| **B. Окно в списке адресов**: `from=<дата>` + `collapse=urlkey` | тот же запрос, но медленнее | адреса, живые в окне; первый снимок **внутри** окна | не самый свежий; мёртвые страницы исчезают из копии |
| **C. Точечный `limit=-1` на каждый адрес** | ×2 запросов к индексу | точный отпечаток самого свежего снимка заранее | при 400 адресах — 400 лишних запросов и риск `429` |

**Рекомендация: A как основной режим + B как параметр.** Способ C не нужен: `Memento-Datetime`
даёт тот же ответ бесплатно, а отпечаток времени нам нужен только для журнала и отчёта.

## 7. План работ (релиз 3.5.0)

### Э1. Режим выбора снимка (ядро задачи)

- `SnapshotMode { Newest, Oldest, At(String) }`; по умолчанию **Newest**.
- `Newest` — цель воспроизведения «сегодня»: `/web/<сегодня>id_/<адрес>`; отпечаток из индекса
  используется только как запасной вариант.
- `Oldest` — текущее поведение (для воспроизводимости и для отчётов, где важна одна эпоха).
- `At("20230301")` — снимок, ближайший к указанной дате (для «копия на дату»).
- CLI: `--snapshot newest|oldest` и `--as-of YYYY[-MM[-DD]]`; в окне — тот же выбор в настройках.
- Требование: **ФТ-126**. Проверка: на `011.vuejs.org` режим `newest` даёт файл 2025 года,
  `oldest` — 2015, содержимое различается.

### Э2. Фактическая дата снимка в журнале и отчёте

- Читать `Memento-Datetime` (и, если есть, `X-Archive-Src`) из ответа; писать в журнал сборки
  рядом с записью файла; показывать в отчёте колонку «снимок» (год-месяц) и в журнале работы —
  сводку «самый старый / самый новый снимок в копии».
- Признак «снимок старше N лет» — предупреждение в отчёте: копия современная лишь настолько,
  насколько свеж архив.
- Требование: **ФТ-127**. Проверка: у копии nginx.org даты 10.11.2026, у 011.vuejs.org — 2025-11.

### Э3. Инкрементальность с учётом свежести

Сейчас журнал пропускает файл, если совпали размер и время изменения **на диске**. При режиме
`newest` это значит: новая копия в архиве не будет замечена никогда.

- В записи журнала хранить дату снимка; при `newest` файл перекачивается, если его снимок старше
  `--refresh-days` (по умолчанию 30) или если пользователь передал `--refresh`.
- `--refresh` — принудительно обновить всё, не меняя копию на диске (сравнение по содержимому:
  размер + хеш при расхождении размеров).
- Требование: **ФТ-128**. Проверка: два прогона подряд — второй не качает; `--refresh` — качает.

### Э4. Окно адресов как параметр

- `--since YYYY[-MM[-DD]]` → `from=` в запросе списка; по умолчанию — без окна (совместимо с 3.4.0).
- Окно применяется к страницам; ресурсы (изображения, стили, скрипты, шрифты) по-прежнему берутся
  из полного списка, иначе современная страница останется без старых картинок.
  Реализация: два запроса — с окном и без; из второго доливаются только не-HTML адреса.
- Предупреждение в отчёте: «адреса ограничены окном с <дата>, файлов вне окна не будет».
- Требование: **ФТ-129**. Проверка: `--since 2024` на 011.vuejs.org — 45 страниц вместо 53,
  картинки на месте.

### Э5. Сопутствующие дефекты (обязательны в этом же релизе)

Они прямо влияют на то, какая версия файла останется в копии:

- **ОШ-11. Один файл — несколько адресов.** `/` и `/index.html`, `/api/` и `/api/index.html`
  дают один путь в копии; после `best` дедупликации нет, файл перезаписывается, победитель
  зависит от порядка потоков. Замеры: 12 адресов → 11 файлов (`011.vuejs.org`), 400 → 150
  (`rustorg`, три поддомена в одном дереве). Решение: дедупликация по локальному пути с приоритетом
  (`/` важнее `/index.html`; при равенстве — более свежий снимок), и **отдельный подсчёт**
  «адресов / файлов / перезаписей» в отчёте.
- **ОШ-12. Поддомены в одном дереве.** Путь в копии строится только из пути адреса, хост не
  участвует (`src/paths.rs:91-121`). `mail.x…`, `mta-sts.x…`, `mx.x…` пишут в один `index.html`.
  Решение: папка по хосту для всех хостов, кроме основного; ссылки на поддомены переписываются
  в эту папку. Обратная совместимость: при одном хосте дерево копии не меняется.

### Э6. Документы и выпуск

- `TZ.md` → 2.9: ФТ-126…ФТ-129, новый раздел о выборе снимка и о том, что «копия не свежее архива»;
  правка §8.3 (счётчики адресов и файлов).
- `docs/DEFECTS.md` → ОШ-11…ОШ-13 (13 — отсутствие даты снимка в журнале).
- `CHANGELOG.md` 3.5.0, `PLAN.md` (Д-43…Д-46), `DESIGN.md` §5.2 и §5.6.
- Тесты: разбор `Memento-Datetime`, режимы `newest/oldest/at`, дедупликация путей, `--refresh`.
- Гейты: `fmt`, `clippy -D warnings` ×2, тесты, `audit`/`deny`/`machete`/`typos`;
  живая проверка на двух сайтах (живой и мёртвый), сравнение годов снимков в отчёте.

## 8. Риски и как их снимаем

| Риск | Проявление | Мера |
|---|---|---|
| Отказы архива `429`/`503`/`504` | прогон «висит» на повторах, окно по времени медленнее | существующие паузы; повторы; окно — параметр, по умолчанию выключено |
| `limit=50000` у больших домов | список обрезан по алфавиту (2008–2015), дальше адресов нет | с окном обрезка уходит; в отчёте писать «список обрезан» |
| Копия «свежая», но архив беден | у мёртвого сайта лучший снимок 2015 | в отчёте сводка годов и предупреждение «снимок старше N лет» |
| Смена поведения по умолчанию | прежние прогоны были воспроизводимы | `--snapshot oldest` возвращает 3.4.0 байт в байт; в CHANGELOG — явное изменение |
| Ресурсы вне окна | современная страница без старых картинок | ресурсы берутся из полного списка (Э4) |
| Разные снимки у связанных файлов | HTML 2026 ссылается на CSS 2019 | нормально для архива; фиксируем годы в отчёте, не «выравниваем» |

## 9. Что остаётся решением владельца

1. Окно по умолчанию: **без окна** (совместимо, но дольше) или **3 года** (быстрее, но старые
   мёртвые адреса не попадут)? Предлагаю без окна, окно — явный параметр.
2. Срок перекачки при `newest`: **30 дней** по умолчанию.
3. Нужен ли режим «копия на дату» (`--as-of`) в интерфейсе или достаточно CLI.

При отсутствии возражений беру в работу по Э1–Э6 с версией 3.5.0.

## 10. Как перепроверить вручную

```powershell
# самый свежий снимок по целевому времени + фактическая дата
curl.exe -sI "https://web.archive.org/web/2026id_/https://011.vuejs.org/" |
  Select-String -Pattern 'Memento-Datetime|x-archive-src'

# тот же адрес, но по нашему текущему отпечатку (2015)
curl.exe -sI "https://web.archive.org/web/20151101133431id_/https://011.vuejs.org/" |
  Select-String -Pattern 'Memento-Datetime'

# последний снимок адреса по индексу
curl.exe -s "https://web.archive.org/cdx/search/cdx?url=011.vuejs.org/&output=json&fl=timestamp&filter=statuscode:200&limit=-1"

# влияние окна на список адресов
curl.exe -s "https://web.archive.org/cdx/search/cdx?url=011.vuejs.org&matchType=domain&output=json&fl=timestamp,original&filter=statuscode:200&collapse=urlkey&from=2025&limit=10"
```

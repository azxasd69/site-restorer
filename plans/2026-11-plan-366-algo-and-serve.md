## 1. Целевая архитектура оптимального алгоритма загрузки (`Д-134`…`Д-137`)

По замерам на `samorez.pro` (`plans/2026-11-multithread-download-samorez.md`) узкое место прогона — не обработка файлов (`0,23–0,63 с` на `150–400` файлов) и не ширина канала (`9,42 МБ` качались `48–231 с`), а четыре дефекта сетевого и многопоточного слоя `3.6.5`.

### 1.1 Постоянный пул соединений (`Д-134`)

| Параметр `ureq::Agent` | Было в `3.6.5` | Становится в `3.6.6` | Основание |
|---|---|---|---|
| `max_idle_connections` (`agent`) | `10` (умолчание) | `64` | Не вытеснять рабочие потоки до `MAX_THREADS` |
| `max_idle_connections_per_host` (`agent`) | `3` (умолчание) | `32` (`>= MAX_THREADS`) | Все запросы идут на один хост `web.archive.org`; убирает `+827 мс` TCP+TLS на каждый запрос сверх `3` |
| `max_idle_age` (`agent` и `agent_index`) | `15 с` | `60 с` | Переживает короткие паузы между файлами и добором |
| `max_idle_connections_per_host` (`agent_index`) | `3` | `4` | Хватает для параллельного обхода страниц CDX |
| Тело ответа при `status != 200` | `drop(body)` | Дренирование до `64 КБ` (`drain_short`) | В HTTP/1.1 непрочитанное тело закрывает сокет в `ureq::Connection::reuse()`; вычитывание коротких `404`/`503` возвращает сокет в пул |

### 1.2 Согласованный `Gate`, потоковый учёт байтов и устойчивый AIMD (`Д-135`)

1. **Согласование потолка `Gate` и `--workers`:**
   - `Gate` хранит `cap = workers.clamp(1, MAX_THREADS)` (`MAX_THREADS = 24`).
   - Начальный лимит: `MIN_THREADS.min(cap)` (для `--workers 1` старт с `1`, для `--workers >= 2` старт с `2`).
   - `set_limit(n)` ограничивает `n.clamp(1, self.cap)`. В UI/CLI `Progress::threads` больше никогда не показывает `24` при `--workers 1`.
   - Рабочие потоки в `download()` создаются числом `self.workers.min(MAX_THREADS)` (при `--workers > 24` лишние потоки ОС не создаются, т.к. `Gate` всё равно не пустит больше `24`).
2. **Потоковое начисление байтов (`save_body`, ФТ-144):**
   - В `save_body()` после записи каждого блока `64 КБ` сразу инкрементируются `counters.bytes` и `counters.win_bytes` (`fetch_add(read as u64, Ordering::Relaxed)`), а в `fetch_one()` после `Attempt::Saved` повторное начисление `bytes`/`win_bytes` убирается.
   - Итог: индикатор `bps` в окне/CLI обновляется плавно даже на одном большом файле, а AIMD больше не видит провалы `0 КБ/с`.
3. **Замер задержки ответа (TTFB) и переработка правил AIMD:**
   - В `Counters` добавляются `win_req_ms: AtomicU64`, `win_req_cnt: AtomicUsize`, `win_overload: AtomicUsize` (считает `503`/`504`/таймауты/`10061` в фазе загрузки).
   - Успешный ответ (или `404`) фиксирует время `open()` в миллисекундах в `win_req_ms`/`win_req_cnt`.
   - Раз в `2 с` (более отзывчивый разгон, при 8 окнах до 16 потоков за ~12–16 с) контроллер пересчитывает `limit`:
     - `if n429 > 0`: `bad_streak += 1`; при `bad_streak >= 3` → `limit = MIN_THREADS.min(cap)`, `pause(120.0)`, `bad_streak = 0`; иначе `limit = (limit / 2).max(1)`.
     - **На любом окне с `n429 == 0`: `bad_streak = 0`** (единичные `429`, разделённые минутами чистой работы, не накапливаются).
     - `else if n_overload > 0`: мягкое снижение при перегрузке `503`/таймаутах/`10061`: `limit = (limit * 3 / 4).max(1)` (минимум `−1` при `limit > 1`), без `120 с` паузы.
     - `else if avg_ms > baseline_ms * 2.5 && avg_ms > 3000.0`: сервер заметно тормозит по времени отклика → `limit = limit.saturating_sub(1).max(1)`.
     - `else if files > 0 || bytes > 0`: **убираем ложное снижение по `bps < prev_speed * 0.6`** (которое срабатывало при переходе от жирного JS к мелким HTML без единой ошибки); при нормальной задержке повышаем `limit = (limit + 1).min(cap)`.
4. **Освобождение слота `Gate` на время сна в `attempt()`:**
   - `attempt()` принимает ссылку на `Gate` (или `Shared::gate` освобождается на время `self.sleep(...)` и снова захватывается перед повтором через RAII-обёртку `GateSlot`). Пока один поток спит `20 с` на `429`, остальные потоки не теряют слот конкурентности.
5. **Оптимальное значение потоков по умолчанию (`DEFAULT_WORKERS`):**
   - Оставляем `--workers 1..=64`, но проверим по итогам замера `3.6.6` на `samorez.pro` (`8` vs `16` с новым пулом keep-alive), какое значение даёт максимум скорости без `503`/`10061`: по фактам `3.6.5` `8` потоков (`105 с` на 400 адресах) обгоняли `16` (`126 с`).

### 1.3 Ускорение `inventory`, `rescue`, быстрая остановка `recheck` и устойчивость к обрывам (`Д-136`, `Д-137`)

1. **Ускоренный постраничный `inventory` (`Д-136`):**
   - При известном `numpages > 1` (`estimate_known && max_pages > 1`) страницы `0..max_pages` запрашиваются пулом из **`min(2, max_pages)` потоков** (щадящая параллельность к CDX API, снижающая время 5 страниц с `120–250 с` в 1,8–2× без лавины `503`), при `503`/`429` сбрасываются к `1` потоку с паузами и **`ARCHIVE_TRIES` (`5`)** попытками на страницу (в 3.6.5 было `3` и хвост индекса терялся).
   - При `HTTP 504` (переключение `domain -> prefix`) страницы перезапускаются с начала, как и раньше.
2. **Параллельный `rescue` (`Д-136`):**
   - Вместо последовательного цикла в 1 поток (`core.rs:4696`), `rescue()` обрабатывает `missing.iter().take(self.rescue_limit)` пулом из `self.workers.clamp(1, 4)` потоков с общим атомарным индексом, общим бюджетом времени `self.rescue_budget` и `Gate`. За отведённые `30 с` бюджет отрабатывает в `~3–4×` больше целей.
3. **Быстрый выход `recheck` и сохранность метаданных при обрыве (`Д-136`):**
   - Поток `recheck` проверяет свой флаг `stop` внутри `fetch_stream_until(..., &stop)`, чтобы после завершения основной очереди он не держал `recheck.join()` лишние `9–60 с`.
   - Во время `download()` каждые `200` завершённых файлов главный цикл периодически сбрасывает на диск `content-types.tsv`, `no-snapshot.tsv` и `snapshots.tsv` (через существующие потокобезопасные методы), чтобы при аварийном обрыве уже скачанные файлы сохраняли свой `Content-Type` и даты снимков.
4. **Прямые багфиксы устойчивости при обрывах (`Д-137`):**
   - **`cleanup_temp()` (`ОШ-15`):** отдельный рекурсивный обход с `long_path` (без фильтра `!is_temp_file` из `walk_files_detailed`), реально удаляющий `.part` и `.jsonl.part` из `mirror` и `data` перед `mirror_list`.
   - **Повтор при обрыве чтения тела внутри `save_body()`:** при `Err(err)` (не `"cancelled"`) в `attempt()` логировать причину через `explain_net(&err)`, спать `0.6 * (attempt + 1)` с (освобождая `Gate`) и **повторять попытку** вместо немедленного `return Attempt::Failed`.
   - **Распознавание `10061` / `10051` на русской Windows (`ОШ-16`):** в `scheme_switch_worthwhile()` добавить `"10061"` и `"10051"`, чтобы локализованная системная ошибка Winsock («Подключение не установлено... (os error 10061)») корректно переключала схему `https → http`.

## 2. Детальная проработка реализации `Д-49`: Встроенный сервер копии (`src/serve.rs`)

### 2.1 Архитектура и выбор транспорта (размер, зависимости, поток)

| Критерий | Вариант с `tiny_http 0.12` (ранний набросок в `DESIGN.md` §5.13) | Выбранный вариант на `std::net::TcpListener` (`3.6.6`) |
|---|---|---|
| Прямые и транзитивные зависимости | `+4` крейта (`tiny_http`, `ascii`, `chunked_transfer`, др.) | **`0` новых крейтов** (`Cargo.toml`, `Cargo.lock`, `SBOM`, `deny.toml` не меняются; соблюдено требование ТЗ §5.2 о числе зависимостей) |
| Прирост размера бинарника | `~200–305 КБ` | **`~15–25 КБ`** (укладывается в лимиты ПР-6 с запасом > 11 МБ на CLI) |
| Потоки | `Arc<Server>`, пул 4 воркера | `Arc<TcpListener>` + канал/очередь задач на пул из **4 воркеров** (`std::thread`), таймауты чтения/записи сокета (`5 с` / `30 с`) |
| Остановка | `server.unblock()` | `AtomicBool` `stop` + неблокирующий цикл `accept` с опросом или пробуждающий loopback-connect к `127.0.0.1:<port>` в `stop()`/`Drop` (мгновенный выход без ожидания) |
| Протокол | HTTP/1.0–1.1 | HTTP/1.1 read-only (`GET`, `HEAD`), потоковая отдача буфером `64 КБ` (файл 1 ГБ не загружается в RAM) |

### 2.2 Функциональность, маршрутизация и безопасность (`ФТ-136`…`ФТ-141`, `БЗ-13`)

1. **Привязка (`БЗ-13`):** только `SocketAddr::from(([127, 0, 0, 1], port))`, где по умолчанию `port = 0` (система выбирает свободный эфемерный порт). Внешние адреса и `0.0.0.0` запрещены на уровне типа.
2. **Публичный API модуля `src/serve.rs`:**
   - `pub struct CopyServer { port: u16, root: PathBuf, stop: Arc<AtomicBool>, threads: Vec<JoinHandle<()>> }`
   - `pub fn resolve_site_dir(path: &Path) -> Option<PathBuf>` — принимает как корень результата (где лежат `site/`, `data/`, `report.html`), так и саму папку `site/`.
   - `pub fn start(root: &Path, port: u16) -> Result<Self, String>` — канонизирует `root` через `core::long_path` + `fs::canonicalize` (учитывая UNC/Windows), поднимает `TcpListener`, запускает `4` воркера и цикл приёма.
   - `pub fn url(&self) -> String` → `http://127.0.0.1:<port>/`
   - `pub fn port(&self) -> u16`
   - `pub fn stop(&mut self)` (и `impl Drop for CopyServer`) — выставляет `stop = true`, совершает короткий контрольный connect на `127.0.0.1:<port>` чтобы разбудить `accept()`, и делает `join()` всех потоков.
3. **Обработка HTTP-запроса:**
   - Чтение строки запроса и заголовков до `\r\n\r\n` (потолок шапки `16 КБ`, защита от зависших клиентов).
   - Метод: только `GET` и `HEAD`. Любой другой метод (`POST`, `PUT`, `DELETE`, …) → `405 Method Not Allowed`, `Allow: GET, HEAD`, `Connection: close`.
   - Проверка цели запроса (`ФТ-137`, `ФТ-140`):
     - обрезаем префикс `http(s)://authority`, если передан полный URL, и `#fragment`;
     - отделяем `raw_path` и `raw_query` по `?`;
     - проверяем каждый сегмент пути до и после `pct_decode`: при наличии `..`, `\`, `\0` → `404 Not Found`;
     - вызываем единую функцию ядра `crate::paths::url_to_local_path(&format!("https://local{target}"))`;
     - если файл не найден и есть `raw_query`, пробуем fallback `crate::paths::url_to_local_path(&format!("https://local{raw_path}"))` (полезно для ассетов `style.css?v=1`, если файл сохранён без query);
     - проверяем, что файл существует, это не каталог (листинг каталогов запрещён!), и `fs::canonicalize` файла начинается с канонического `canon_root` (`starts_with`) → иначе `404 Not Found`.
4. **Заголовки и режимы отдачи (`ФТ-138`, `ФТ-139`):**
   - `Content-Type`: строго по расширению файла **без** `; charset=...` (кодировку задаёт сам документ; для `html/htm` → `text/html`, `css` → `text/css`, `js/mjs` → `application/javascript`, `json` → `application/json`, `xml` → `application/xml`, `svg` → `image/svg+xml`, `png` → `image/png`, `jpg/jpeg` → `image/jpeg`, `gif` → `image/gif`, `webp` → `image/webp`, `ico` → `image/x-icon`, `bmp` → `image/bmp`, `woff` → `font/woff`, `woff2` → `font/woff2`, `ttf` → `font/ttf`, `otf` → `font/otf`, `eot` → `application/vnd.ms-fontobject`, `pdf` → `application/pdf`, `mp4` → `video/mp4`, `webm` → `video/webm`, `txt` → `text/plain`, по умолчанию `application/octet-stream`).
   - `ETag`: `W/"<len>-<mtime_secs>"` (по размеру и времени изменения). Если `If-None-Match` содержит этот `ETag` → `304 Not Modified` без тела.
   - `Accept-Ranges: bytes`, `Cache-Control: no-cache`, `Connection: close`.
   - Заголовок `Range`: поддерживаются `bytes=A-B`, `bytes=A-`, `bytes=-N`. При некорректном формате или выходе за границы (`start >= len`, `start > end`, пустой файл при запросе диапазона) → `416 Range Not Satisfiable` + `Content-Range: bytes */<len>`. При валидном диапазоне → `206 Partial Content`, `Content-Range: bytes <start>-<end>/<len>`, `Content-Length: <chunk_len>`.
   - `HEAD` отдаёт те же статус и заголовки (вкл. `200`/`206`/`416`/`304`/`404`), но без тела.

### 2.3 Интеграция в CLI, GUI и отчёт

1. **CLI (`src/main.rs`, `ФТ-141`):**
   - Новые флаги: `--serve <папка>` и опциональный `--port <N>` (`0..=65535`, по умолчанию `0`).
   - Работает без `--cli` и без `--site` (проверка в `main()`: `console_mode` включает `--serve`).
   - Определяет папку через `serve::resolve_site_dir`, при ошибке папки или порта печатает понятное сообщение (RU/EN) и возвращает код `1` (неверный флаг/порт → `2`).
   - Печатает `сервер копии: http://127.0.0.1:<порт>` (`copy server: ...`), ждёт `Ctrl+C` (Windows: `SetConsoleCtrlHandler`, Unix: `libc::signal(SIGINT/SIGTERM)`) и корректно останавливает сервер с кодом `130` (или `0`).
2. **GUI (`src/app.rs`, `src/i18n.rs`, `ФТ-136`):**
   - Новая кнопка на главной панели рядом с «Открыть папку»: **«Открыть копию»** (RU) / **«Open copy»** (EN); когда сервер запущен — **«Остановить сервер»** / **«Stop server»**.
   - По первому клику поднимает `CopyServer::start`, пишет в журнал `сервер копии: http://127.0.0.1:<порт>` и открывает адрес через `crate::links::open(&url)`.
   - По второму клику останавливает сервер, пишет в журнал `сервер копии остановлен`.
   - При изменении `self.out` или при закрытии окна (`on_exit`) активный сервер останавливается, порт освобождается.
3. **Отчёт `report.html` (`src/core.rs`):**
   - В подвале отчёта `{{t_footer}}` добавить подсказку точной команды встроенного сервера: `site-restorer --serve "<путь к папке>"` (либо кнопка «Открыть копию» в окне).
